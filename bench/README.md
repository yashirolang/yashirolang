# bench/ — 速さを測る

**この文書とロードマップに載っている数字は、ここで測ったものです。**

```bash
make                 # 先にコンパイラを作る
bench/run.sh         # 全部
bench/run.sh mat     # 種目を選ぶ（loop / fp / mat / compile / selfhost）
BENCH_REPS=5 bench/run.sh   # 繰り返し回数（既定 3。最小値を採る）
```

`rustc` / `python3` / `numpy` は**無くても動きます**（その行が「（なし）」になります）。
作った実行ファイルは `bench/out/` に入り、git では追跡しません。

---

## 測り方の約束

**2026-09-02 の敵対的レビュー（[../docs/roadmap.md](../docs/roadmap.md) §3-B）で、
以前の測り方に 3 つの問題が見つかりました。ここはその修正版です。**

### ① プロセスの起動時間を引き算しない

以前は「外から測った総時間 − 起動 4 ms」でした。ところが **C 側の総時間が
9 ms しかなく**、4 ms を引くと分母が半分になって、比が実際より小さく出ていました
（「C の 5.1 倍」は本当は 8 倍でした）。

いまは**どのプログラムも自分の中で時計を読み**、測りたいループだけの時間を
`TIME_MS` として出します。

| 言語 | 使う時計 |
|---|---|
| yashirolang | `lib/time` の `time.monotonic_ns()` |
| C | `bench_time.h` の `clock_gettime(CLOCK_MONOTONIC)` |
| Rust | `std::time::Instant` |
| Python | `time.perf_counter()` |

起動時間そのものは「何もしないプログラム」の行として**別に**出します
（引き算はしません）。

### ② 最適化の水準を必ず書く

`yashirolang prog.ys` の既定は **`-O0`** です。`-O2` とは 5〜8 倍違います。
表では `-O0`（既定）と `-O2` を別の行にしています。

### ③ 答え合わせをする

各プログラムは `RESULT` も出し、`run.sh` が C の値と突き合わせます。
**速いが間違っている**を弾くためです。

## 種目

| 種目 | 見ているもの |
|---|---|
| `loop` | 整数の算術 2000 万回。**桁あふれ検査の費用**が出ます |
| `fp` | float の級数 2000 万項 |
| `mat` | 行列積 512³。二重リスト（`list[list[float]]`）と `linalg.Matrix`（平坦）の 2 通り |
| `compile` | コンパイルの速さ。`-S`（コンパイラ本体の仕事だけ）と、clang 込みの実行ファイル生成 |
| `selfhost` | 自分自身の型検査（C 版 stage0 とセルフホスト版 stage1） |

### 比較対象について

- **Rust** は既定（`-O`）では**桁あふれを検査しません**。yashirolang は検査するので、
  `-C overflow-checks=on` の行も出します。**比べるならこちらです。**
- **numpy** の `a @ b` は BLAS（ブロック化・SIMD・マルチスレッド）です。
  **同じ土俵ではありません。** 上限の目安として置いてあります。
- yashirolang に並行実行はないので、**すべて単スレッド同士**の比較です。

### N を 512 にしている理由

256 では C の総時間が 10 ms 以下になり、測定の揺れと起動時間が
比を歪めます。512 なら C でも 30 ms 以上あり、比が安定します
（N を変えても比はほぼ変わらないことは §3-B1 で確かめました）。
