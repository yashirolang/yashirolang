# LLVM IR 生成規約

> `codegen.c` を書くときの取り決めです。
> **迷ったらここに書いてあるルールに従う**ことで、コード生成器が一貫した形に保たれます。
>
> LLVM IR そのものの文法を知らない場合は、先に
> LLVM IR の入門資料を先に読んでください。

## 1. 最重要の設計判断：「全部 alloca 方式」

これがこの教材で最も重要な設計判断です。

### 問題：LLVM IR は SSA 形式である

LLVM IR のレジスタ（`%t0` など）は **SSA (Static Single Assignment)** です。
つまり **1 回しか代入できません**。

```llvm
%x = add i64 1, 0
%x = add i64 2, 0    ; ✗ エラー: %x が 2 回定義されている
```

しかし yashirolang のソースはこう書けます。

```python
x: int = 1
x = 2
x = x + 1
```

これを SSA にするには、変数のバージョンを追跡し、
分岐が合流する地点に `phi` 命令を挿入する必要があります。

```llvm
; if 文の後で x の値を合流させる
merge:
  %x.3 = phi i64 [ %x.1, %then ], [ %x.2, %else ]
```

**この `phi` 挿入アルゴリズム（SSA 構築）は、コンパイラ理論の中でも難所です。**
支配辺境（dominance frontier）の計算が必要で、初学者が最初に取り組むものではありません。

### 解決：すべての変数をメモリ（スタック）に置く

**変数を SSA レジスタにせず、`alloca` で確保したスタック領域に置きます。**

```python
x: int = 1
x = 2
y: int = x + 1
```

```llvm
define i32 @main() {
entry:
  %x = alloca i64              ; ← 変数 x のための箱をスタックに確保
  %y = alloca i64
  store i64 1, ptr %x          ; x = 1
  store i64 2, ptr %x          ; x = 2   （何度でも store できる！）
  %t0 = load i64, ptr %x       ; x を読む
  %t1 = add i64 %t0, 1
  store i64 %t1, ptr %y        ; y = x + 1
  ret i32 0
}
```

**メモリへの `store` は SSA の制約を受けません。** 何回でも書き込めます。
`phi` は一切不要になります。

### これは遅くないのか？

生成直後の IR は遅いです（毎回メモリアクセスする）。
しかし **LLVM の `mem2reg` パスが、この形を自動的に SSA + phi に変換します。**

```
「全部 alloca」の IR  ──[ mem2reg ]──▶  最適な SSA + phi の IR
```

`mem2reg` は LLVM の最も基本的な最適化パスで、`-O1` 以上で必ず走ります。
つまり **私たちは素朴に書き、LLVM が賢く直す**。

### ✅ 実際に確認してみる

```bash
# 素朴な IR を書く
cat > /tmp/naive.ll <<'EOF'
define i64 @f(i64 %n) {
entry:
  %x = alloca i64
  store i64 %n, ptr %x
  %t0 = load i64, ptr %x
  %t1 = add i64 %t0, 1
  store i64 %t1, ptr %x
  %t2 = load i64, ptr %x
  ret i64 %t2
}
EOF

# mem2reg を掛ける
$(brew --prefix llvm)/bin/opt -passes=mem2reg -S /tmp/naive.ll
```

出力：

```llvm
define i64 @f(i64 %n) {
entry:
  %t1 = add i64 %n, 1
  ret i64 %t1
}
```

**alloca / store / load が完全に消えました。**
これがこの方式を採用できる理由です。

### ルール

> **R1. すべてのローカル変数・引数は、関数の entry ブロックで `alloca` する。**
> **R2. 変数の読み出しは `load`、書き込みは `store`。SSA レジスタに変数を割り当てない。**
> **R3. `phi` 命令は生成しない。**

**⚠️ 例外**：短絡評価（`and`/`or`）の結果は `phi` で受けるほうが自然に見えますが、
一貫性のため**そこも `alloca` を使います**。

## 2. モジュールの構造

生成する `.ll` ファイルの全体構成を固定します。

```llvm
; ── ①ヘッダ ──────────────────────────────
; Generated by yashirolang
source_filename = "hello.ys"
target triple = "x86_64-apple-macosx26.0.0"

; ── ②型定義 ──────────────────────────────
%Token.type = type { i64, ptr }
%list.type  = type { ptr, i64, i64 }

; ── ③グローバル変数・文字列定数 ─────────────
@.str.0 = private unnamed_addr constant [6 x i8] c"hello\00"
@g.counter = global i64 0

; ── ④外部関数宣言 ─────────────────────────
declare i32 @puts(ptr)
declare ptr @malloc(i64)
declare void @pl_print_int(i64)

; ── ⑤関数定義 ────────────────────────────
define i64 @add(i64 %a.arg, i64 %b.arg) {
entry:
  ...
}

define i32 @main() {
entry:
  ...
}
```

### ⚠️ `.ll` はモジュールごとに 1 本

`import` を入れると「1 ファイル = 1 モジュール = 1 `.ll`」になります。
上の構成はそのままで、
**②〜⑤に「他モジュールのもの」が混ざる**点だけが変わります。

| 要素 | 自分のモジュール | import したモジュール |
|---|---|---|
| クラスの型 | `%main.Box.type = type { i64 }` | `%lexer.Token.type = type { i64, ptr }`（**同じ定義を複製する**） |
| 関数 | `define ptr @main.f(...)` | `declare ptr @lexer.make(i64, ptr)` |
| グローバル変数 | `@g.main.n = global i64 0` | `@g.lexer.MAX = external global i64` |

**LLVM の型定義はモジュールローカル**なので、使う側の `.ll` にも同じ定義を書きます。
レイアウトの計算はコンパイラのプロセス内で 1 回だけ行い、`Class *` を共有するので、
2 つの `.ll` が食い違うことはありません。

### `target triple` を必ず出力する

```llvm
target triple = "x86_64-apple-macosx26.0.0"
```

**⚠️ これを書かないと clang が警告を出します。**

```
warning: overriding the module target triple with x86_64-apple-macosx26.0.0
         [-Woverride-module]
```

実装では、ビルド時に**その環境の clang 自身が使う triple** を取得して埋め込みます。

```makefile
# clang が実際に .ll に書く triple を取り出す
HOST_TRIPLE := $(shell $(CC) -S -emit-llvm -x c /dev/null -o - 2>/dev/null \
                 | sed -n 's/^target triple = "\(.*\)"$$/\1/p')
CFLAGS += -DPLC_TARGET_TRIPLE='"$(HOST_TRIPLE)"'
```

**⚠️ ここに実際に踏んだ落とし穴があります。**
直感的には `clang -print-target-triple` を使いたくなりますが、**これでは警告が消えません。**

```bash
$ clang -print-target-triple
x86_64-apple-darwin25.5.0          # ← こちらを .ll に書くと…

$ clang tt.ll -o tt
warning: overriding the module target triple with x86_64-apple-macosx26.0.0
         [-Woverride-module]       # ← 警告が出る！

$ clang -S -emit-llvm -x c /dev/null -o - | grep 'target triple'
target triple = "x86_64-apple-macosx26.0.0"    # ← こちらが正解
```

macOS の clang は、`-print-target-triple`（`darwin<カーネル版>`）と
IR に書く triple（`macosx<OS版>`）で**異なる表記**を使います。
後者を使わないと毎回警告が出ます。

**🤔 なぜハードコードしないのか**：Intel Mac / Apple Silicon / Linux で値が違います。
「clang 自身に聞く」方式なら、どの環境でも警告なしに動きます。

### 4 つの出力バッファ

`codegen.c` は上記 ①〜⑤ に対応するバッファを持ち、最後に連結します。

```c
typedef struct {
    StrBuf header;    // ①②  型定義
    StrBuf globals;   // ③    グローバル・文字列定数
    StrBuf decls;     // ④    declare
    StrBuf body;      // ⑤    関数定義
} Emitter;
```

関数本体を生成中に文字列リテラルに出会ったら、`globals` に追記します。
出力順序に悩まなくなるのがこの分割の利点です。

## 3. 名前の付け方（命名規約）

LLVM IR には 3 種類の名前があります。

| 記号 | 種類 | スコープ |
|---|---|---|
| `@name` | グローバル（関数・グローバル変数・定数） | モジュール全体 |
| `%name` | ローカル（レジスタ・alloca・ラベル） | 関数内 |
| `%Name.type` | 型 | モジュール全体（慣習） |

### ルール

| 対象 | 規約 | 例 |
|---|---|---|
| トップレベル関数 | `@モジュール名.関数名` | `@lexer.tokenize` |
| クラスのメソッド | `@モジュール名.クラス名.メソッド名` | `@lexer.Token.is_eof` |
| `main` | `@main`（LLVM の `i32 @main()`）。入口モジュールの `main` を呼ぶラッパ | `@main` |
| `extern` 関数 | 修飾しない | `@malloc` |
| ランタイム関数 | `@pl_` プレフィックス | `@pl_print_int` |
| グローバル変数 | `@g.` + モジュール名 + `.` + 名前 | `@g.lexer.counter` |
| 文字列定数 | `@.str.N`（N は連番） | `@.str.0` |
| クラスの型 | `%モジュール名.クラス名.type` | `%lexer.Token.type` |
| ローカル変数の alloca | `%変数名` | `%x` |
| 引数の一時名 | `%変数名.arg` | `%a.arg` |
| 一時値（レジスタ） | `%t.N`（**'.' を含める**） | `%t.0`, `%t.1` |
| 基本ブロックのラベル | 用途名 + `.N` | `if.then.0`, `while.cond.1` |

### ⚠️ 一時値の名前には '.' を入れます

`%tN` のままだと、**利用者が `t0` という変数を書いたときに衝突します**。

```llvm
  %t0 = alloca ptr        ; 利用者の変数 t0
  %t0 = load ptr, ...     ; コンパイラの一時値 → error: multiple definition
```

stage1（セルフホスト版コンパイラ）の移植中に実際に踏みました。
利用者の識別子に `.` は入れられないので、**`.` を含む名前にすれば
衝突は原理的に起きません**（脱糖が作る隠し変数 `for.ix.0` と同じ手口）。

**★ 過去の記述に載っている IR の抜粋は `%t0` のままです**
（その時点のコンパイラが出していたものなので、書き換えません）。

### ⚠️ 一時値カウンタは関数ごとにリセットする

```c
static int tmp_counter;   // 関数の生成開始時に 0 に戻す
static char *new_tmp(void) {
    char *buf = xmalloc(24);
    snprintf(buf, 24, "%%t%d", tmp_counter++);
    return buf;
}
```

**⚠️ 落とし穴**：LLVM は「名前のない値」に暗黙の連番（`%0`, `%1`, ...）を振ります。
自分で `%t0` のように**名前を付けておけば衝突しません**。
逆に `%0` のような数値名を自分で使うと、LLVM の暗黙採番とぶつかって
`error: instruction expected to be numbered '%2'` のような分かりにくいエラーが出ます。

> **R4. 一時値には必ず英字始まりの名前を付ける（`%t0` など）。数値だけの名前は使わない。**

### ⚠️ ラベル名も一意にする

```llvm
if.then.0:      ; 1 個目の if
  ...
if.then.1:      ; 2 個目の if（ネストしていても衝突しない）
```

同じ関数内で `if.then` を 2 回使うとエラーになります。**必ず連番を付けます。**

## 4. 型のマッピング

| yashirolang | LLVM（値） | LLVM（メモリ） |
|---|---|---|
| `int` | `i64` | `i64` |
| `bool` | `i1` | `i8` |
| `float` | `double` | `double` |
| `str` | `ptr` | `ptr` |
| `None` | `void` | — |
| `list[T]` | `ptr` | `ptr` |
| class `C` | `ptr` | `ptr` |

### ⚠️ opaque pointer について

**LLVM 15 以降、ポインタ型は型情報を持ちません。** すべて `ptr` です。

```llvm
; 昔（LLVM 14 以前）
%p = alloca i64
%v = load i64, i64* %p

; 今（LLVM 15 以降）
%p = alloca i64
%v = load i64, ptr %p
```

古い解説記事は `i8*` や `i64*` を使っているので注意してください。
**この教材ではすべて `ptr` で書きます。**

`load` / `store` / `getelementptr` は、ポインタが指す型を**命令側で明示**します。

```llvm
%v = load i64, ptr %p              ; ptr の先を i64 として読む
store i64 42, ptr %p               ; ptr の先に i64 として書く
%q = getelementptr i64, ptr %p, i64 3   ; i64 3 個分進める
```

### bool の変換規約

> **R5. `bool` はメモリ上 `i8`、レジスタ上 `i1`。境界で `zext`/`trunc` する。**

```llvm
; store: i1 → i8
%t1 = zext i1 %cond to i8
store i8 %t1, ptr %flag

; load: i8 → i1
%t2 = load i8, ptr %flag
%t3 = trunc i8 %t2 to i1
```

## 5. 式のコード生成

### 5.1 基本パターン：`gen_expr` は「値を保持するレジスタ名」を返す

```c
// 式を生成し、結果の値が入っているレジスタ名（"%t3" など）を返す
static char *gen_expr(Emitter *e, Node *n);
```

**この関数シグネチャがコード生成器の設計を決めます。**
「式を生成する」＝「命令列を出力し、結果の置き場所の名前を返す」です。

### 5.2 整数リテラル

命令を出力する必要すらありません。**即値をそのまま返します。**

```c
case ND_INT: {
    char *buf = xmalloc(24);
    snprintf(buf, 24, "%lld", n->ival);
    return buf;      // "42" という文字列を返す
}
```

`add i64 42, 1` のように、LLVM は即値をオペランドに直接書けるからです。

### 5.3 二項演算

```python
a + b
```

```c
case ND_BINOP: {
    char *l = gen_expr(e, n->lhs);
    char *r = gen_expr(e, n->rhs);
    char *t = new_tmp();
    sb_printf(&e->body, "  %s = %s %s %s, %s\n",
              t, llvm_op(n->op, n->type), llvm_type(n->type), l, r);
    return t;
}
```

```llvm
%t2 = add i64 %t0, %t1
```

### 演算子の対応表

| yashirolang | 型 | LLVM 命令 |
|---|---|---|
| `+` | int | `add i64` |
| `-` | int | `sub i64` |
| `*` | int | `mul i64` |
| `//` | int | `sdiv i64` |
| `%` | int | `srem i64` |
| `&` | int | `and i64` |
| `\|` | int | `or i64` |
| `^` | int | `xor i64` |
| `<<` | int | `shl i64` |
| `>>` | int | `ashr i64`（算術シフト） |
| `+` | float | `fadd double` |
| `-` | float | `fsub double` |
| `*` | float | `fmul double` |
| `/` | float | `fdiv double` |
| `==` | int | `icmp eq i64` |
| `!=` | int | `icmp ne i64` |
| `<` | int | `icmp slt i64` |
| `<=` | int | `icmp sle i64` |
| `>` | int | `icmp sgt i64` |
| `>=` | int | `icmp sge i64` |
| `==` | float | `fcmp oeq double` |
| `<` | float | `fcmp olt double` |
| `+` | str | `call ptr @pl_str_concat(ptr, ptr)` |
| `==` | str | `call i1 @pl_str_eq(ptr, ptr)` |
| `**` | int | `call i64 @pl_ipow(i64, i64)` |

**⚠️ 符号に注意**：`int` は符号付きなので `sdiv`（`udiv` ではない）、
`icmp slt`（`ult` ではない）、`ashr`（`lshr` ではない）を使います。
間違えると負数で誤動作します。

### 5.4 単項マイナス

LLVM に `neg` 命令はありません。`sub` で表現します。

```llvm
%t1 = sub i64 0, %t0        ; -x
%t1 = fneg double %t0       ; float はこちら（fneg はある）
%t1 = xor i64 %t0, -1       ; ~x
```

### 5.5 変数の読み書き

```llvm
; 読み出し（ND_VAR）
%t0 = load i64, ptr %x

; 書き込み（ND_ASSIGN）
store i64 %t0, ptr %x
```

### 5.6 関数呼び出し

```llvm
; 戻り値がある場合
%t3 = call i64 @add(i64 %t0, i64 %t1)

; 戻り値が None（void）の場合 → レジスタに受けない
call void @pl_print_int(i64 %t0)
```

**⚠️ `void` を返す `call` に `%t = ` を付けるとエラーです。**
`gen_expr` は `None` 型の場合、ダミーの文字列（`""`）を返す設計にします。

## 6. 制御フローのコード生成

### 6.1 基本ブロックの規則

> **R6. すべての基本ブロックは、必ず 1 つの終端命令（terminator）で終わる。**

終端命令は `ret`, `br`, `switch`, `unreachable` のいずれかです。

```llvm
; ✗ エラー: 終端命令がない
entry:
  %t0 = add i64 1, 2
next:
  ...

; ✅ 正しい
entry:
  %t0 = add i64 1, 2
  br label %next        ; ← 明示的にジャンプする
next:
  ...
```

**⚠️ これが初心者が最もよくハマる落とし穴です。**
「次のブロックに続くだけ」でも `br label %next` が必要です。
C の実行フローとは違い、**IR にはフォールスルーがありません。**

### 6.2 到達不能ブロックの処理

`return` の直後にコードがある場合、そこは新しいブロックになります。

```python
return 1
x = 2      # 到達不能
```

```llvm
  ret i64 1
dead.0:                  ; ← ラベルを作らないと後続の命令が置けない
  store i64 2, ptr %x
  unreachable            ; ← 終端命令が必要
```

> **R7. ブロックを終端した後にコードを生成する必要が生じたら、`dead.N` ラベルを作る。**

実装では「現在のブロックが終端済みか」を追跡するフラグを持ちます。

```c
typedef struct {
    ...
    bool terminated;   // 現在のブロックが終端命令を出力済みか
} Emitter;

static void emit_label(Emitter *e, const char *label) {
    if (!e->terminated)
        sb_printf(&e->body, "  br label %%%s\n", label);   // 暗黙のジャンプを補う
    sb_printf(&e->body, "%s:\n", label);
    e->terminated = false;
}
```

**この 1 つの関数が、基本ブロックの落とし穴のほとんどを吸収します。**

### 6.3 if 文

```python
if cond:
    A
else:
    B
C
```

```llvm
  %t0 = <cond の生成>          ; i1
  br i1 %t0, label %if.then.0, label %if.else.0

if.then.0:
  <A の生成>
  br label %if.end.0

if.else.0:
  <B の生成>
  br label %if.end.0

if.end.0:
  <C の生成>
```

`else` がない場合は、`if.else.0` の代わりに `if.end.0` へ直接分岐します。

```llvm
  br i1 %t0, label %if.then.0, label %if.end.0
```

`elif` は「else の中に if がある」ものとして再帰的に生成します（脱糖）。

### 6.4 while 文

```python
while cond:
    BODY
```

```llvm
  br label %while.cond.0

while.cond.0:
  %t0 = <cond の生成>
  br i1 %t0, label %while.body.0, label %while.end.0

while.body.0:
  <BODY の生成>
  br label %while.cond.0        ; ループバック

while.end.0:
```

**⚠️ `while.cond` に入る前に `br label %while.cond.0` が必要です。**
条件評価は毎回行われるので、条件のブロックは独立させます。

### 6.5 break / continue

現在のループの「脱出先」と「継続先」をスタックで管理します。

```c
typedef struct LoopCtx LoopCtx;
struct LoopCtx {
    LoopCtx *outer;
    char *break_label;      // while.end.N
    char *continue_label;   // while.cond.N
};
```

- `break` → `br label %while.end.N`
- `continue` → `br label %while.cond.N`
- ループの外で使われたら sema がエラーにする

### 6.6 短絡評価（and / or）

```python
a and b
```

「結果を alloca に置く」方式で書きます（R1 の一貫性）。

```llvm
  %and.result.0 = alloca i8
  %t0 = <a の生成>                          ; i1
  %t1 = zext i1 %t0 to i8
  store i8 %t1, ptr %and.result.0
  br i1 %t0, label %and.rhs.0, label %and.end.0

and.rhs.0:
  %t2 = <b の生成>                          ; i1
  %t3 = zext i1 %t2 to i8
  store i8 %t3, ptr %and.result.0
  br label %and.end.0

and.end.0:
  %t4 = load i8, ptr %and.result.0
  %t5 = trunc i8 %t4 to i1                  ; ← これが a and b の値
```

`or` は分岐の真偽を逆にするだけです。

```llvm
  br i1 %t0, label %or.end.0, label %or.rhs.0
```

**⚠️ `alloca` は entry ブロックに置く**（R1）。
上の例では読みやすさのために現地に書いていますが、実装では entry にまとめます。

## 7. 関数のコード生成

```python
def add(a: int, b: int) -> int:
    return a + b
```

```llvm
define i64 @add(i64 %a.arg, i64 %b.arg) {
entry:
  %a = alloca i64                ; 引数もローカル変数として扱う
  %b = alloca i64
  store i64 %a.arg, ptr %a       ; 引数の値を alloca にコピー
  store i64 %b.arg, ptr %b
  %t0 = load i64, ptr %a
  %t1 = load i64, ptr %b
  %t2 = add i64 %t0, %t1
  ret i64 %t2
}
```

> **R8. 引数は `%名前.arg` で受け取り、entry で `alloca` にコピーする。**

**🤔 なぜコピーするのか**：引数 `%a.arg` は SSA レジスタなので代入できません。
yashirolang では引数に代入できる（`a = a + 1`）ので、ローカル変数と同じ扱いにします。
`mem2reg` がこの余分なコピーを消してくれます。

### `main` の特別扱い

yashirolang の `main` は `int` を返しますが（`i64`）、C の `main` は `i32` を返します。

```llvm
define i32 @main(i32 %argc, ptr %argv) {
entry:
  %t0 = sext i32 %argc to i64
  call void @pl_set_args(i64 %t0, ptr %argv)   ; sys.argv() のため
  %t1 = call i64 @main.main()                  ; 入口モジュールの main
  %t2 = trunc i64 %t1 to i32
  ret i32 %t2
}
```

**⚠️ 呼ぶ相手の名前は章によって変わりました。**

| 版 | ラッパが呼ぶ関数 | 備考 |
|---|---|---|
| 旧 | `@pl_main` | C の `main` と衝突しないための名前 |
| 現行 | `@<入口モジュール>.main` | モジュール修飾が衝突よけの役目を引き取った |

**★ `argc` / `argv` を受け取るようになりましたが、
利用者の `main` も AST も 1 行も変わっていません。**
ラッパ方式（下記の方式 A）の効果です。

方式は 2 つあります。

| 方式 | 説明 |
|---|---|
| A. ラッパを作る | ユーザーの `main` を `@pl_main` として出力し、`@main` を別に生成 |
| B. 直接 i32 で出す | `main` だけ戻り型を `i32` にし、`return` 時に `trunc` する |

**この教材では A を採用します。**
`main` を他の関数と同じ規則で扱えるため、コード生成器に特別分岐が減ります。
また将来 `main` から例外的な初期化処理（ランタイム初期化など）を挟みやすくなります。

### 戻り値のない関数

```llvm
define void @f() {
entry:
  ...
  ret void            ; ← 明示的な return がなくても必要
}
```

> **R9. 戻り型が `None` の関数は、本体の最後に `ret void` を必ず出力する。**

## 8. データ構造のコード生成

### 8.1 文字列リテラル

```python
"hello"
```

```llvm
; 旧表現
@.str.0 = private unnamed_addr constant [6 x i8] c"hello\00"

; 現行（★ 長さを前に置く）
@.str.0 = private unnamed_addr constant { i64, [6 x i8] } { i64 5, [6 x i8] c"hello\00" }
```

**⚠️ 表現を途中で変えました。**

```
[ i64 長さ ][ バイト列 ... ][ '\0' ]
             ^ str の「値」が指すのはここ
```

`len(s)` と `s[i]` が毎回 `strlen` していたため、1 文字ずつ回るコードが
O(n²) になっていたからです（実測）。
長さを 8 バイト手前に置くと `pl_str_len` が O(1) になります。

**値が指すのはデータの先頭のまま**なので、C から見れば今までどおり
NUL 終端の `char *` です（`extern` にそのまま渡せます）。

使うときはデータ部を指す定数式を書きます。

```llvm
call void @pl_print_str(
    ptr getelementptr inbounds ({ i64, [6 x i8] }, ptr @.str.0, i32 0, i32 1))
```

**⚠️ `extern` で C の関数が `str` を返す場合、その文字列も
「長さ付き」でなければなりません**（`pl_str_alloc` / `pl_str_from_cstr` を使う）。
`argv` のような素の C 文字列は、そのままでは yashirolang の `str` になりません。

**⚠️ エスケープの書き方**：IR の文字列リテラルでは、印字不能文字を `\XX`（16進 2 桁）で書きます。

| 文字 | IR での表記 |
|---|---|
| 改行 | `\0A` |
| タブ | `\09` |
| NUL | `\00` |
| `"` | `\22` |
| `\` | `\5C` |

安全策として、**ASCII 印字可能文字以外はすべて `\XX` にエスケープする**方針にします。

### 8.2 グローバル変数

```python
counter: int = 0
```

```llvm
@g.counter = global i64 0
```

使用時は `alloca` と同じく `load`/`store` します（すでにポインタなので `alloca` 不要）。

```llvm
%t0 = load i64, ptr @g.counter
store i64 %t1, ptr @g.counter
```

### 8.3 list[T]

```llvm
%list.type = type { ptr, i64, i64 }   ; data, len, cap
```

生成・操作はランタイム関数に委譲します（IR を単純に保つため）。

```llvm
%t0 = call ptr @pl_list_new(i64 8)              ; 要素サイズ
call void @pl_list_push_i64(ptr %t0, i64 42)
%t1 = call i64 @pl_list_get_i64(ptr %t0, i64 0)
%t2 = call i64 @pl_list_len(ptr %t0)
```

**🤔 なぜ IR で直接インライン展開しないのか**：
`append` は「容量が足りたら書き込む、足りなければ 2 倍に realloc」という分岐を含みます。
これを IR で展開すると生成コードが読めなくなります。
**複雑な処理は C のランタイム関数に押し出し、IR は `call` 1 行に保つ**のが方針です。
`-O2` でインライン展開されるので、性能上の損失もほぼありません。

> **R10. 制御フローを含む処理は、IR に展開せずランタイム関数の呼び出しにする。**

**⚠️ R10 には例外が 2 つあります。**
`xs[i]` の**境界検査**と、`obj.f` の **None 検査**は IR に展開します。

理由は「`-O2` でインライン展開されるので性能上の損失もほぼない」という
上の前提が、**この 2 つでは成り立たなかった**ためです。ランタイムは
`build/runtime.a` として別にリンクされ、LTO を使っていないので
インライン化されません。添字とフィールド参照はこの言語で最も回数の多い
操作で、行列積の内側ループが関数呼び出し 5 回になり、**C の 61 倍**
遅くなっていました（IR に展開して 5.1 倍）。

| | R10 に従う | 例外にする |
|---|---|---|
| 判断の分かれ目 | 処理そのものが重い（`append` の realloc、`pl_ipow` のループ） | **検査だけで、当たりの経路は命令数個**（`icmp` 1〜2 個） |
| 例 | `append` / `pl_floordiv` / `pl_str_concat` | `gen_index_addr` / `gen_not_none` |

外れの経路（`pl_index_fail` / `pl_none_fail`）は呼び出しのままです。
**戻らない**ので、IR は直後に `unreachable` を置きます。

⚠️ `-flto` を足す案も試しましたが、**効果はほぼゼロ**でした
（319 ms → 313 ms）。呼び出しを消すのはリンカではなく codegen の仕事です。

#### 戻らない関数には `noreturn` と `cold` の両方を付ける

```llvm
declare void @pl_panic(ptr) noreturn cold
declare void @pl_exit(i64) noreturn cold
declare void @pl_index_fail(i64, i64, i64) noreturn cold
declare void @pl_none_fail() noreturn cold
```

**この 2 つは別の働きをします。**

| 属性 | LLVM に伝えること | これが無いと |
|---|---|---|
| `noreturn` | 呼んだら戻ってこない | panic の後ろの経路が生き、ループ内の load を外に出せない |
| `cold` | **その経路はまず通らない** | panic の手前の処理が**インライン化の費用として満額数えられる** |

**`cold` が無いと何が起きたか。** 利用者はふつう、失敗したときに
役に立つメッセージを書きます。

```python
def check(self, i: int, j: int) -> None:
    if i < 0 or i >= self.rows or j < 0 or j >= self.cols:
        panic("linalg.Matrix: 添字が範囲外です（" + str(i) + ", " + str(j) + "）")
```

当たりの経路は比較 4 つですが、**外れの経路が連結 4 回 ＋ `str()` 2 回**です。
LLVM はこれを `check` の大きさとして数え、既定のしきい値を超えるので
`check` を**丸ごとインライン化しません**。`check` は `Matrix.get` / `set` から、
つまり行列積の内側ループから 1 周に 3 回呼ばれていました。

`cold` を付けるとその経路が割り引かれ、`check` は `get` / `set` ごと
呼び出し元に畳まれます。**行列積 256³ が 143 ms → 62 ms** になりました。

⚠️ **利用者側にも同じ形があります。** メッセージの組み立てを検査関数の中に
直接書くと、`cold` を付けてもその関数の中の連結は数えられます。
`lib/linalg.ys` では `Matrix.index_fail` として**別関数に切り出して**あります。
片方だけでは効きません（切り出しだけでは 140 ms のまま、`cold` だけでは
100 ms、両方で 62 ms）。

⚠️ ただし**切り出す価値があるのは「ループの中から呼ばれる検査」だけ**です。
`linalg.same_len` は `add` / `sub` / `mul` のループの**外**で 1 回呼ばれる
だけなので、切り出しても速くなりません（測ったら 0.31 → 0.34 秒で、
少し遅くなったので戻しました）。

#### ⚠️ `cold` でも「呼び出しがあること」自体の費用は消えません

当初は「`cold` を付ければ外れの経路は割り引かれる」と考えていました。
**割り引かれるのは経路の中身だけで、呼び出しが 1 つあること自体は数えられます。**
しかし桁あふれ検査を入れたら、`linalg.Matrix` の行列積がまた 2.6 倍
遅くなり、LLVM に直接聞いて分かりました。

```console
$ clang -O2 -Rpass-missed=inline ...
remark: 'linalg.Matrix.get' not inlined into 'linalg.matmul'
        because too costly to inline (cost=225, threshold=225)
```

IR を書き換えて確かめた内訳です。

| 外れの経路の書き方 | インライン化されるか |
|---|---|
| `call void @pl_overflow_fail(i64 2)` | ❌ されない |
| 引数を無くした `call void @pl_overflow_fail0()` | ❌ されない（**引数は関係ない**） |
| `call void @llvm.trap()`（組み込み命令） | ✅ される |
| `unreachable` だけ | ✅ される |

**外れの経路の呼び出し 1 つにつき約 25 点**です。`Matrix.get` には
外れの経路が 5 つあり、225 点のうち約 125 点が「一度も通らない経路」でした。

> **R13. 外れの経路の「呼び出しの数」を増やさない。** `cold` を付けても
> 1 つにつき約 25 点かかる。小さなメソッド（`get` / `set`）はこれで
> インライン化のしきい値を越える。

**この規則に従った結果が、添字の中の桁あふれ検査です。**
分岐せずに旗（`i1`）を立て、**もとからある範囲検査に相乗り**させます。

```llvm
  %ovf = or i1 %mo, %ao          ; 添字の中の + - * の旗をまとめる
  %inb = icmp ult i64 %idx, %len
  %nov = xor i1 %ovf, true
  %ok  = and i1 %inb, %nov       ; ★ 範囲内 かつ あふれていない
  br i1 %ok, label %idx.ok.4, label %idx.bad.4
idx.bad.4:
  call void @pl_index_fail(i64 %idx, i64 %len, i64 %z)   ; ★ 呼び出しは 1 つのまま
  unreachable
```

`pl_index_fail` の 3 つめの引数が「あふれたか」です（`zext i1`）。
あふれたときの `%idx` は折り返した値で意味がないので、
ランタイムは数を出さず `integer overflow in index computation` と言います。

⚠️ **健全性**：折り返した添字がたまたま範囲内に入っても、`and` で
潰しているので必ず失敗します（`tests/cases/rt_overflow_index.ys`）。

⚠️ **添字の外の算術は今までどおり**、演算ごとにその場で分岐します
（`gen_checked_arith`）。相乗りできる検査が無いためです。

#### 別名解析（TBAA）の型タグ

**すべてのモジュールの末尾に、この 7 行を必ず出します**（使っていなくても）。
2 実装が 1 バイト違わない IR を出すため、番号は固定です。

```llvm
!0 = !{!"<言語名>"}              ; 根（langinfo が決める）
!1 = !{!"field",    !0}            ; クラスのフィールド
!2 = !{!"listhdr",  !0}            ; list のヘッダ（data ポインタと len）
!3 = !{!"listelem", !0}            ; list の要素
!4 = !{!1, !1, i64 0}              ; ↑ へのアクセスタグ
!5 = !{!2, !2, i64 0}
!6 = !{!3, !3, i64 0}
```

| タグを付ける場所 | 付けない場所 |
|---|---|
| クラスのフィールドの load / store（`gen_field` / フィールドへの代入） | ローカル変数（alloca）・グローバル |
| list のヘッダ（`data` と `len`。`gen_index_addr`） | 文字列・`unsafe:` の生ポインタ・`extern` |
| list の要素（`gen_index` / `gen_index_store`） | vtable・エラースロット |

**健全性**：`pl_list_new` はヘッダと要素配列を別々に確保し、クラスの
オブジェクトもまた別の確保なので、3 つは決して重なりません。
**タグの無いアクセスは「何とでも別名かもしれない」**と扱われるため、
迷ったら付けないのが安全側です。

> **R14. 新しい種類のメモリを触るときは、タグを付けるより先に
> 「本当に重ならないか」を確かめる。** 重なりうるなら付けない。

実測は同じ IR から `!tbaa` だけを `sed` で削って A/B しました
（行列積が二重リスト −16% / `linalg` −8%）。

⚠️ **ベクトル化は開きません。** TBAA は別名を外すだけで、
**境界検査の分岐は減らしません**。
最初に測ったときは 142 ms → 146 ms で効果ゼロでしたが、
**それはインライン化が詰まっていたからでした。** `cold` を入れてから
測り直すと、クラスのフィールド／list のヘッダ／list の要素に
別々の型タグを付けることで **60 ms → 48 ms（−20%）** になります。
設計と健全性の確認は `docs/roadmap.md` の §3-A1 にあります。

**教訓：「効かなかった」は「そのときのボトルネックでは効かなかった」でしかありません。**

### 8.4 class

```python
class Token:
    kind: int
    text: str
```

```llvm
%Token.type = type { i64, ptr }
```

インスタンス生成：

```llvm
%t0 = call ptr @malloc(i64 16)                     ; sizeof(Token) = 8 + 8
call void @Token.init(ptr %t0, i64 1, ptr @.str.0)
```

フィールドアクセス `t.kind`（インデックス 0）：

```llvm
%t1 = getelementptr %Token.type, ptr %t0, i32 0, i32 0
%t2 = load i64, ptr %t1
```

`t.text`（インデックス 1）：

```llvm
%t3 = getelementptr %Token.type, ptr %t0, i32 0, i32 1
%t4 = load ptr, ptr %t3
```

**⚠️ `getelementptr` の 2 つのインデックスの意味**

```llvm
getelementptr %Token.type, ptr %t0, i32 0, i32 1
              ^^^^^^^^^^^        ^^^^^^  ^^^^^^
              ベースの型          │       │
                                 │       └─ 構造体の何番目のフィールドか
                                 └─ その型の何個目の要素か（配列的な移動）
```

第 1 インデックスは「`Token` を配列とみなして何個目か」です。
単一のオブジェクトを触るときは常に `0` です。**ここを間違えると全く別のアドレスを読みます。**

サイズとオフセットの計算は、コンパイラ側で行います（アラインメント規則は C と同じ）。

```c
// 各フィールドのオフセットとクラス全体のサイズを計算
int offset = 0;
for (Field *f = cls->fields; f; f = f->next) {
    int align = type_align(f->type);
    offset = (offset + align - 1) / align * align;   // 切り上げ
    f->offset = offset;
    offset += type_size(f->type);
}
cls->size = (offset + cls->align - 1) / cls->align * cls->align;
```

## 9. デバッグの手順

生成した IR が動かないときの調べ方です。

### 手順 1: IR が文法的に正しいか

```bash
yashirolang -S foo.ys              # foo.ll を出力
$(brew --prefix llvm)/bin/llvm-as foo.ll -o /dev/null
```

エラーが出れば IR の文法ミスです。行番号が出るので追えます。

### 手順 2: 検証器を通す

```bash
$(brew --prefix llvm)/bin/opt -passes=verify -S foo.ll -o /dev/null
```

「終端命令がない」「型が合わない」などの構造的な問題を検出します。

### 手順 3: そのまま実行してみる

```bash
$(brew --prefix llvm)/bin/lli foo.ll ; echo "exit=$?"
```

`lli` は IR をその場でインタプリタ実行します。**コンパイル・リンクを省略できて速い**です。

### 手順 4: 最適化前後を比べる

```bash
$(brew --prefix llvm)/bin/opt -passes=mem2reg -S foo.ll
$(brew --prefix llvm)/bin/opt -O2 -S foo.ll
```

「自分の生成が冗長なのか、LLVM が消してくれるのか」がわかります。

### 手順 5: C から正解を教わる

**最強の手法です。** 同じ意味の C コードを書いて、clang に IR を吐かせます。

```bash
cat > /tmp/ref.c <<'EOF'
long f(long a, long b) { return a + b; }
EOF
clang -S -emit-llvm -O0 /tmp/ref.c -o -
```

「この機能はどう IR にすればいいのか」が分からないときは、
**まず C で書いて clang に見せてもらう**。これで 9 割解決します。

## 10. 規約まとめ（チートシート）

| # | 規約 |
|---|---|
| R1 | すべてのローカル変数・引数は entry ブロックで `alloca` する |
| R2 | 変数の読み書きは `load`/`store`。SSA レジスタに変数を割り当てない |
| R3 | `phi` 命令は生成しない |
| R4 | 一時値には英字始まりの名前を付ける（`%t0`）。数値名は使わない |
| R5 | `bool` はメモリ上 `i8`、レジスタ上 `i1`。境界で `zext`/`trunc` |
| R6 | すべての基本ブロックは終端命令で終わる |
| R7 | 終端後にコードが必要なら `dead.N` ラベルを作る |
| R8 | 引数は `%名前.arg` で受け、entry で `alloca` にコピー |
| R9 | 戻り型 `None` の関数は本体末尾に `ret void` |
| R10 | 制御フローを含む処理はランタイム関数呼び出しにする（⚠️ 添字の境界検査と None 検査は例外。8.3 節） |
| R11 | `target triple` を必ず出力する |
| R12 | ポインタ型は常に `ptr`（opaque pointer） |
| R13 | 外れの経路の**呼び出しの数**を増やさない（`cold` でも 1 つ約 25 点。8.3 節） |
| R14 | TBAA のタグは「決して重ならない」と確かめた場所にだけ付ける（8.3 節） |
| R15 | **同じ値は同じ形で読む**。片方が `call`、片方が `load` だと LLVM は同一視できない（`len` は load。8.3 節） |

## デバッグ情報（A-30）

`-g` のときだけ、LLVM の debug metadata を出します。

| 規約 | 内容 |
|---|---|
| R14 | metadata の番号は **10 から**振る（0〜8 は TBAA が固定で使う。9 は空け） |
| R15 | モジュールに 1 組だけ要るもの（`!DIFile` / `!DICompileUnit` / `!{}` / `!DISubroutineType`）は**関数より先に**作る（番号が 2 実装で同じになるため） |
| R16 | 行の `!DILocation` は**行ごとに 1 つ**だけ作る（文ごとに作ると metadata が膨らむ） |
| R17 | 命令への `!dbg` は**後付け**で付ける。飛ばすのはラベル行・空行・すでに `!dbg` がある行 |
| R18 | `-g` を付けないときの出力は**1 バイトも変えない** |

⚠️ **`!llvm.module.flags` に「Debug Info Version」を書かないと、clang は
metadata を丸ごと捨てます**（黙って消えるので、気づくのに時間がかかります）。
