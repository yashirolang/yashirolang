# セルフホスト計画

> 最終目標である「yashirolang で書いた yashirolang コンパイラが自分自身をコンパイルできる」状態への
> 道筋と、達成を検証する方法を定義します。

---

## 1. セルフホストとは何か

```
【今】
  stage0 (C で書かれた実行ファイル)  +  foo.ys  →  foo (実行ファイル)

【目標】
  stage1 (この言語で書かれた実行ファイル)  +  selfhost/*.ys  →  stage1 と同じもの
```

コンパイラが**自分自身のソースコードをコンパイルできる**状態です。

### 🤔 なぜこれを目標にするのか

1. **言語が実用に足ることの最も厳しい証明**
   コンパイラは、文字列処理・データ構造・再帰・ファイル入出力・大規模なコード整理を
   すべて必要とします。それが書けるなら、その言語は実用言語です。

2. **バグを自分で踏むことになる**
   自分の言語で数千行を書くと、設計の不便な点が容赦なく明らかになります。
   「型注釈が冗長すぎる」「エラーメッセージが不親切」を、**自分が最初のユーザーとして体験**します。

3. **鶏と卵の問題を解く経験**
   「コンパイラを書くにはコンパイラが必要」というパラドックスを、
   ブートストラップという手法で解きます。これは計算機科学の古典的な美しさの 1 つです。

---

## 2. ブートストラップの仕組み

「鶏と卵」は、**すでに存在する別のコンパイラを踏み台にする**ことで解けます。

```
                     ┌─────────────────────────────────────┐
                     │  ソースコード（変わらない）            │
                     │  selfhost/*.ys                      │
                     └─────────────────────────────────────┘
                                    │
   ┌────────────────────────────────┼────────────────────────────────┐
   │                                │                                │
   ▼                                ▼                                ▼
┌──────────┐  compiles    ┌──────────┐  compiles    ┌──────────┐  compiles  ┌──────────┐
│ stage0   │─────────────▶│ stage1   │─────────────▶│ stage2   │───────────▶│ stage3   │
│ (C 製)   │              │(yashirolang 製)│              │(yashirolang 製)│            │(yashirolang 製)│
└──────────┘              └──────────┘              └──────────┘            └──────────┘
   ↑                                                     │                       │
   │                                                     └────── 比較 ───────────┘
C で先に作る                                                        │
                                                            一致 ⇒ 成功 🎉
```

### 各 stage の意味

| stage | 何で書かれているか | 何でコンパイルされたか |
|---|---|---|
| **stage0** | C 言語 | Apple clang（外部のコンパイラ） |
| **stage1** | yashirolang | stage0 |
| **stage2** | yashirolang | stage1 |
| **stage3** | yashirolang | stage2 |

### 🤔 なぜ stage1 と stage2 は一致しなくてよいのか

**ここがブートストラップで最も混乱しやすい点です。**

stage1 と stage2 は、**同じソースから作られた**のに一致しないことがあります。

```
stage1 = stage0(selfhost/*.ys)      ← C 製コンパイラの出力
stage2 = stage1(selfhost/*.ys)      ← セルフホスト版コンパイラの出力
```

理由：**stage0 と stage1 は「別のコンパイラ」だから**です。
両者は同じ言語仕様を実装していますが、実装が違います。たとえば：

- stage0（C 版）は一時レジスタ名を `%t0, %t1, ...` と振る
- stage1（セルフホスト版）はたまたま評価順が違い、`%t0, %t2, %t1` と振る

どちらも**意味は同じで正しい**IR ですが、バイト列としては違います。
だから stage1 ≠ stage2 でも問題ありません。

一方、

```
stage2 = stage1(selfhost/*.ys)
stage3 = stage2(selfhost/*.ys)
```

**stage2 と stage3 は一致しなければなりません。**
なぜなら stage1 と stage2 は「同じソースを同じ仕様で実装したセルフホスト版コンパイラ」であり、
**stage2 が正しく stage1 と同じ振る舞いをするなら、その出力も同じ**になるはずです。

これを **不動点（fixed point）に到達した**と言います。

```
f = 「selfhost/*.ys をコンパイルする」という関数
stage2 = f(stage1)
stage3 = f(stage2)
stage2 == stage3  ⇔  stage2 は f の不動点  ⇔  セルフホスト成功
```

### ⚠️ もし stage2 ≠ stage3 だったら

それは **stage1 にバグがある**という意味です。具体的には：

- stage1 が生成した stage2 が、stage1 と違う振る舞いをする
- つまり stage1 のコード生成に「自分自身を正しく再現できない」欠陥がある

デバッグ手順の基本は
「stage1 と stage2 に同じ小さな入力を与えて、出力 IR を diff する」です。

## 3. セルフホストに必要な言語機能のチェックリスト

**このチェックリストを全部埋めることが到達目標でした。**

> ## ★ 達成（2026-08-23）
>
> ```
> $ make bootstrap
> ★ stage2 と stage3 が出す IR が完全一致（13 本）
> ★ 不動点に到達しました（stage2 == stage3）
> ```
>
> このドキュメントの計画どおりに進み、セルフホストに到達しました。

**★ 2026-08-22 に全項目の判断が終わりました。**
以降は、このリストに載っているものだけで書いています。
すべて ✅ になれば、yashirolang でコンパイラが書けます。

### 3.1 基本

| 機能 | 必要な理由 | 状態 |
|---|---|---|
| `int` 型と算術演算 | カウンタ、オフセット計算 | ⬜ |
| `bool` と比較・論理演算 | 条件判定のすべて | ⬜ |
| `if` / `elif` / `else` | 分岐（トークン種別の判定など） | ⬜ |
| `while` / `break` / `continue` | 字句解析のループ | ⬜ |
| 関数定義・呼び出し | コードの整理 | ⬜ |
| **再帰呼び出し** | **再帰下降パーサに必須** | ⬜ |
| 全経路 return 検査 | バグ防止（必須ではないがあると助かる） | ⬜ |

### 3.2 文字列（コンパイラの主戦場）

| 機能 | 必要な理由 | 状態 |
|---|---|---|
| `str` 型とリテラル | ソースコードそのもの、IR の出力 | ⬜ |
| `len(s)` | 走査の終了判定 | ⬜ |
| `s[i]`（1 文字取得） | 字句解析の 1 文字読み | ⬜ |
| `a + b`（連結） | IR 文字列の組み立て | ⬜ |
| `a == b`（内容比較） | キーワード判定 | ⬜ |
| `str(n)`（int → str） | レジスタ番号 `%t42` の生成 | ⬜ |
| `int(s)`（str → int） | 整数リテラルのパース | ⬜ |
| `ord(c)` / `chr(n)` | 文字の分類（数字か英字か） | ⬜ |
| 部分文字列 `substr(s,i,n)` | トークンのテキスト切り出し | ✅ `strings.substr`（O(n²)。3.6 参照） |
| エスケープ処理 | 文字列リテラルの扱い | ⬜ |

**⚠️ 文字列機能が最も重要です。** コンパイラは本質的に文字列処理プログラムです。
文字列まわりで手を抜くと、移植の途中で必ず戻ってくることになります。

### 3.3 データ構造

| 機能 | 必要な理由 | 状態 |
|---|---|---|
| `list[T]` の生成・`append` | トークン列、引数リスト、文のリスト | ⬜ |
| `xs[i]` の読み書き | 任意位置アクセス（パーサの先読み） | ⬜ |
| `len(xs)` | 走査 | ⬜ |
| `for x in xs` | 走査 | ⬜ |
| `for i in range(n)` | インデックス走査 | ⬜ |
| `class` とフィールド | **Token / Node / Type の表現** | ⬜ |
| メソッド | 整理（`tok.is_keyword()` など） | ⬜ |
| **`T \| None`** | **AST の子ノードが無い場合（`else` 節なし等）** | ✅ |
| `list[Node]`（参照型のリスト） | 文のリスト、引数リスト | ⬜ |
| `dict[str, X]`（あるいは線形探索の代替） | シンボルテーブル | ✅ `dict.Dict`（str→int の線形探索） |

**⚠️ `T | None` は必須です。** AST のノードは
「`else` 節がある/ない」「型注釈が解決済み/未解決」のような
**「値が無い」状態を必ず持ちます**。これが表現できないと AST が書けません。

**🤔 `dict` は本当に必要か**
シンボルテーブルは線形探索（`list` を舐める）でも動きます。
`dict` は用意しますが、**間に合わなければ線形探索で先に進んでよい**です。
コンパイラの速度はセルフホスト到達後に測って直します。

### 3.4 入出力

| 機能 | 必要な理由 | 状態 |
|---|---|---|
| `print(s)` | IR の出力、デバッグ | ⬜ |
| ファイル全体の読み込み | ソースコードを読む | ✅ `io.read_file` |
| ファイルへの書き込み | `.ll` を出力する | ✅ `io.write_file` |
| コマンドライン引数の取得 | `yashirolang foo.ys -o foo` | ✅ `sys.argv` |
| 外部コマンド実行（`system`） | `clang foo.ll -o foo` を呼ぶ | ✅ `sys.run` |
| 終了コード指定（`exit(n)`） | エラー時の終了 | ⬜ |
| stderr への出力 | エラーメッセージ | ⬜ |

**⚠️ 見落としやすい項目**：`argv` の取得と `system()` 呼び出しです。
これがないと、セルフホスト版コンパイラは「コマンドラインツール」になれません。
必ず入れます。

### 3.5 プログラムの整理

| 機能 | 必要な理由 | 状態 |
|---|---|---|
| `import`（複数ファイル） | 4000 行を 1 ファイルに書きたくない | ✅ |
| `extern def` | C ランタイムを呼ぶ | ✅ |
| グローバル変数 | 現在位置などのコンパイラ状態 | ⬜ |

### 3.6 標準ライブラリを yashirolang で書いて見つかった穴

**★ 自分の言語で標準ライブラリを書くと、言語の穴が出てきます。**
`lib/strings.ys` / `lib/dict.ys` を書きながら「これが無いと不便だ」と
思ったものを記録します。

| 見つかった穴 | どう回避したか | 結論 |
|---|---|---|
| **`T \| None` が無い** | `find` は「見つからない」を `-1` で返す。`dict.get` は panic | ✅ **入れた**（型 + 絞り込み） |
| **文字列の 1 文字アクセスが毎回ヒープ確保** | `s[i]` が 1 文字の `str` を返す | ✅ `strings.byte_at`（extern）を追加。**ただし実測したら主犯は別だった**（下） |
| **`len(s)` / `s[i]` が毎回 `strlen` していた** | （気づいていなかった） | ✅ **str の表現を「長さ付き」に変えた**。O(n) → O(1) |
| **文字列の連結が O(n²)** | `out = out + x` を繰り返していた | ✅ `pl_str_join` をランタイムに追加。「`list[str]` に溜めて最後に `join`」が定石 |
| 文字列スライス `s[a:b]` が無い | `strings.substr()` を書いた | ❌ 入れない（トークンの切り出しは短いので `substr` で足りる） |
| `in` 演算子が無い | `strings.contains()` を書いた | ❌ 入れない（関数で足りる） |
| 利用者定義のジェネリクスが無い | `dict.Dict` は `str → int` 限定。値は `list[T]` の添字で持つ | ❌ 入れない（ハンドル方式で足りる） |
| 複数戻り値が無い | クラスを返す／`list` を返す | ❌ 入れない |

### 3.7 意図的に「不要」と判断した機能

セルフホストに**要らない**ものを明記します。これを作らない判断が完成を早めます。

| 機能 | なぜ不要か |
|---|---|
| クロージャ / 第一級関数 | 再帰下降パーサは関数の直接呼び出しで書ける |
| 継承 / インターフェース | `Node` は「全部入り構造体」方式（[architecture.md](architecture.md) 3.2）で表現する |
| 例外 | エラーは `panic()` で即終了する方針 |
| ジェネリクス（ユーザー定義） | `list[T]` の組み込み対応で足りる |
| 演算子オーバーロード | 使わない |
| タプル / 複数戻り値 | class を返せば済む |
| イテレータプロトコル | `for` は `list` と `range` に限定 |
| 文字列フォーマット（f-string） | `"a" + str(n) + "b"` で書ける（冗長だが動く） |
| GC | [memory-model.md](memory-model.md) 参照 |
| モジュールの循環 import | ファイル構成を DAG に保つ |

**🤔 f-string について**
`"%s = add i64 %s, %s"` 相当が書けないと IR 生成が非常に冗長になります。
しかし `+` と `str()` の組み合わせで書けるので、**言語機能としては不要**です。
代わりに**ヘルパ関数**を用意します。

```python
# lib/strutil.ys
def cat3(a: str, b: str, c: str) -> str:
    return a + b + c

def cat5(a: str, b: str, c: str, d: str, e: str) -> str:
    return a + b + c + d + e
```

これで IR 生成がこう書けます。

```python
emit(cat5("  ", t, " = add i64 ", l, ", " + r))
```

美しくはありませんが、**言語機能を増やさずに問題を解決**しています。
この種のトレードオフ判断が、言語設計の実践です。

## 4. 移植の順序と検証方法

**各段階で C 版が「正解」を持っている**ことを最大限に活用します。

### lexer.ys

```bash
# 同じ入力に対するトークン列を比較する
./build/yashirolang      --dump-tokens tests/cases/all_syntax.ys > /tmp/c.txt
./build/stage1-lexer --dump-tokens tests/cases/all_syntax.ys > /tmp/m.txt
diff /tmp/c.txt /tmp/m.txt && echo "✅ 一致"
```

**★ `--dump-tokens` を最初から作っておく理由がここにあります。**
これがあるから、字句解析器だけを独立して検証できます。

### parser.ys

```bash
./build/yashirolang       --dump-ast tests/cases/all_syntax.ys > /tmp/c.txt
./build/stage1-parser --dump-ast tests/cases/all_syntax.ys > /tmp/m.txt
diff /tmp/c.txt /tmp/m.txt && echo "✅ 一致"
```

AST を **S 式**で出力するのは、テキスト比較できるようにするためです。

```
(func main () int
  (block
    (return (binop + (int 1) (binop * (int 2) (int 3))))))
```

### sema.ys

型検査は「通る/通らない」と「エラーメッセージ」が出力です。

```bash
# 型エラーのテストケースすべてで、両者が同じエラーを出すか
for f in tests/cases/err_*.ys; do
    a=$(./build/yashirolang      "$f" 2>&1 >/dev/null)
    b=$(./build/stage1-sema  "$f" 2>&1 >/dev/null)
    [ "$a" = "$b" ] || echo "❌ $f"
done
```

### codegen.ys

```bash
./build/yashirolang        -S tests/cases/all_syntax.ys -o /tmp/c.ll
./build/stage1-codegen -S tests/cases/all_syntax.ys -o /tmp/m.ll
diff /tmp/c.ll /tmp/m.ll && echo "✅ IR 完全一致"
```

**⚠️ ここで完全一致を目指すべきか？**

目指すべきです。理由：**一致していれば、それ以上の検証が不要**になります。
「意味は同じだが表記が違う」を許すと、比較のたびに人間が判断する必要が生じます。

そのために、C 版とセルフホスト版で**同じアルゴリズム・同じ順序**で実装します。
機械的な移植（1 行ずつ書き写す）が最も安全です。**ここで独創性を発揮しないこと。**

### ブートストラップ

```bash
make bootstrap
```

```makefile
# Makefile
SELF = selfhost/main.ys

bootstrap: build/yashirolang
	@echo "── stage1: C 製コンパイラでセルフホスト版コンパイラをビルド ──"
	./build/yashirolang $(SELF) -o build/stage1

	@echo "── stage2: stage1 で自分自身をビルド ──"
	./build/stage1 $(SELF) -o build/stage2

	@echo "── stage3: stage2 で自分自身をビルド ──"
	./build/stage2 $(SELF) -o build/stage3

	@echo "── 不動点の検証 ──"
	@if cmp -s build/stage2 build/stage3; then \
		echo "✅ stage2 == stage3 : セルフホスト達成！"; \
	else \
		echo "❌ stage2 != stage3 : stage1 にバグがあります"; \
		exit 1; \
	fi
```

**⚠️ バイナリ比較の前に IR で比較する**ほうがデバッグしやすいです。

```bash
./build/stage1 -S $(SELF) -o /tmp/s2.ll
./build/stage2 -S $(SELF) -o /tmp/s3.ll
diff /tmp/s2.ll /tmp/s3.ll        # 差分が見える形で出る
```

バイナリの `cmp` は「違う」しか教えてくれません。**IR の diff なら原因が読めます。**

## 5. selfhost/ のファイル構成

C 版と 1:1 に対応させます。

| C 版 | セルフホスト版 | 内容 |
|---|---|---|
| `src/main.c` | `selfhost/main.ys` | 引数処理、パス起動 |
| `src/util.c` | `lib/strutil.ys` ほか | 文字列ヘルパ（標準ライブラリへ） |
| `src/lexer.c` | `selfhost/lexer.ys` | 字句解析 |
| `src/ast.c` | `selfhost/ast.ys` | Node クラス定義とダンプ |
| `src/types.c` | `selfhost/types.ys` | Type クラス |
| `src/parser.c` | `selfhost/parser.ys` | 構文解析 |
| `src/sema.c` | `selfhost/sema.ys` | 型検査 |
| `src/codegen.c` | `selfhost/codegen.ys` | IR 出力 |
| `src/diag.c` | `selfhost/diag.ys` | エラー報告 |

**この 1:1 対応を崩さないこと。** 崩すと「C 版のどこを見れば正解がわかるか」が失われます。

## 6. よくある失敗と対策

| 失敗 | 症状 | 対策 |
|---|---|---|
| 文字列機能が足りない | 移植の途中で行き詰まる | 3.2 のチェックリストを全部埋める |
| `T \| None` を後回しにした | AST が定義できない | クラスより先に必ず実装する |
| C 版と違うアルゴリズムで書いた | 出力が一致せず原因が追えない | **機械的に移植する。工夫しない** |
| 一気に全部移植した | どこが壊れたかわからない | ファイル単位で、C 版と差分検証しながら進める |
| `argv` / `system()` を忘れた | stage1 がコマンドとして動かない | 3.4 のチェックリストで確認 |
| stage2 ≠ stage3 で途方に暮れる | — | IR で diff。小さい入力から二分探索 |
| stage1 が遅すぎる | ビルドに数分かかる | 線形探索を `dict` に置換。ただし完成後 |

## 7. 到達後にできること

セルフホストしたら、C 版（stage0）は**もう要らなくなります**。
言語の改良を yashirolang 自身で行えます。

```
新機能を実装する（yashirolang で書く）
  → stage2 でコンパイル → stage3（新機能を持つコンパイラ）
  → stage3 で自分をコンパイル → stage4
```

**⚠️ ただし C 版は捨てないでください。**
新機能のバグで stage が壊れたとき、stage0 から作り直せることが最後の保険になります。
これを「ブートストラップの退路」と呼びます。

### 到達後の課題

✅ **f-string・ジェネリクス・エラー処理（`raises`）は、その後入りました。**
残っているのは次のものです（[roadmap.md](../roadmap.md) と重なります）。
