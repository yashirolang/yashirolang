# 言語の外側との境界（FFI）の設計

**C の関数を呼ぶ向き（`extern`）と、外から呼ばれる向き（本体つきの `extern`）。
後者の目的は「Python のライブラリを yashirolang で書けること」です。**

> **現在地** — 段階 1（§8）は **0.41.0 で入りました**。C 版とセルフホスト版の両方にあり、
> 生成する IR も .py も 2 つの実装で一致します。Python から実際に呼ぶ試験は
> `tests/python.sh`（`make test` に含まれます。python3 が無ければ飛ばします）。
>
> **この機能はここで完了です。** 段階 2・3 として予定していたものは入れません（§8）。

> **前提** — 言語仕様を壊さないことが最初の条件です。
>
> - **新しいキーワードを 1 つも足しません。** `extern` はもう予約語です。
> - **既存のコードの意味は 1 つも変わりません。** 本体つきの `extern def` は
>   これまで構文エラーだった形です。そこに意味を与えるだけです。
> - **「clang だけで建つ」を守ります。** コンパイラの構築にも、ライブラリの
>   構築にも Python のヘッダは要りません（§6）。
> - **アンワインドは入れません。** `raises` はいままでどおり戻り値検査です。

---

## 1. 決めたこと

| | |
|---|---|
| 採った | **`extern def` に本体を書くと「外へ出す関数」になる**（§2） |
| 採った | 境界では**値を写す**。借りは境界を越えない（§4） |
| 採った | 外へ出す関数は、呼び先までたどって**グローバルを書き換えない**（検査。§5） |
| 採った | `raises` は Python の例外に、`panic` も**境界で**例外に変える（§5） |
| 採った | Python 側は **ctypes を使う .py を生成する**（§6） |
| 採った | `int` と `float` は境界でも**混ぜない**（Python 側で `TypeError`） |
| ✗ 捨てた | `export` という新しいキーワード、`@export` のような飾り |
| ✗ 捨てた | Python の C API（`Python.h`）を直接使う拡張モジュール |
| ✗ 捨てた | 引数を借りのまま渡す（Python の list をそのまま触らせる） |
| ✗ 捨てた | クラスを外に見せること（所有権が境界を越えます。§8） |

## 2. 書き方

```python
# stats.ys
class EmptyError:
    message: str

    def init(self, message: own str) -> None:
        self.message = message

extern def mean(xs: list[float]) -> float raises EmptyError:
    if len(xs) == 0:
        raise EmptyError("空の list の平均は決まりません")
    s: float = 0.0
    for x in xs:
        s = s + x
    return s / float(len(xs))

extern def greet(name: str, times: int = 1) -> str:
    return (name + "! ") * times
```

```console
$ yashirolang --python stats.ys -o out/
$ ls out/
_stats.dylib   stats.py
```

```python
>>> import stats
>>> stats.mean([1.0, 2.0, 4.0])
2.3333333333333335
>>> stats.mean([])
stats.EmptyError: 空の list の平均は決まりません
>>> stats.greet("yo", times=2)
'yo! yo! '
>>> stats.mean([1, 2])
TypeError: mean: 'xs' の要素は float です（int が渡されました。float(x) にしてください）
```

**`extern def` の中身は、ふつうの関数とまったく同じです。** 所有権・範囲外の
検査・桁あふれの検査・契約（`requires` / `ensures`）がすべてそのまま効きます。
モジュールの中から呼ぶときも、ふつうの関数として呼べます。

### 2.1 なぜ `extern` なのか

| 案 | 判断 |
|---|---|
| **本体つきの `extern def`** | **採用。** C でも `extern` は「翻訳単位の外から見える」という意味です。本体の無い `extern` が「外にあるものを呼ぶ」、本体のある `extern` が「外から呼ばせる」で、**同じ語が境界の両向きを表します** |
| `export def` | 予約語が 1 つ増えます（ロードマップ ①「注釈を増やさない」） |
| `@export` の飾り | 飾り（デコレータ）という**仕組みごと**増えます |
| `extern` の一覧を別ファイルに書く | 関数と「外に出す」という事実が離れて、ずれます |

**★ 書くのは定義側に 1 回だけです**（ロードマップ ①「`own` / `mut` は定義側に 1 回」と同じ考え）。

## 3. 境界に出せる型

段階 1 で出せるのは、**写して意味が変わらない型**だけです。

| yashirolang | C の ABI（引数） | C の ABI（戻り値） | Python |
|---|---|---|---|
| `int` | `int64_t` | `int64_t` | `int`（範囲外は `OverflowError`。`bool` は断る） |
| `float` | `double` | `double` | `float`（`int` は断る） |
| `bool` | `int64_t`（0 / 1） | `int64_t` | `bool`（`int` は断る） |
| `str` | `const char *`, `int64_t`（UTF-8 と長さ） | 取っ手 | `str` |
| `list[int]` / `list[float]` / `list[bool]` | 先頭のポインタ, `int64_t`（要素数） | 取っ手 | `list` |
| `list[str]` | `const char **`, `const int64_t *`, `int64_t` | 取っ手 | `list[str]` |
| 戻り値の `None` | — | なし | `None` |

**出せないもの**（`E-EXPORT-1`）：クラス・`rc[T]`・`T | None`・タプル・列挙・
関数型・`mutex[T]`・`Thread[R]`・`ptr[T]`・入れ子の list。

注意: **`bool` を `int64_t` で渡すのは、`extern`（C を呼ぶ向き）が `bool` を
禁じているのと同じ理由です。** `i1` と C の `_Bool` の ABI は環境によって違います。

注意: **`int` と `float` を混ぜないのは、境界でも同じです**（ロードマップ ②）。
Python では `mean([1, 2])` が通るのが普通ですが、ここで黙って `float` にすると
「どこで精度が落ちたか」を追えなくなるという理由が、そのまま当てはまります。
直し方は Python 側で `float(x)` と書くことです（エラーの文面がそれを言います）。

### 3.1 なぜ写すのか

借りのまま渡すと、**Python 側のオブジェクトが yashirolang の所有権検査の外**に
なります。Python のスレッドが呼び出し中に list を書き換えれば、`for` の途中で
list が入れ替わるのと同じことが起きます（0.40.0 の `E-BORROW-9` が止めた形です）。

写せば、**呼び出しの中にある値はすべて、その呼び出しが所有します**。
境界の内側は、ふつうの yashirolang のコードとまったく同じ規則で守られます。

| 代償 | 大きさ |
|---|---|
| 写す時間 | 要素数に比例（`list[float]` の 100 万要素で数 ms）。計算が O(n) 以上なら埋もれます |
| `mut` 引数が使えない | 写しを書き換えても Python には戻らないので、**断ります**（`E-EXPORT-2`）。結果は戻り値で返します |

## 4. ABI（C から見た形）

### 4.1 名前

**`<モジュール名>_<関数名>`** です（パッケージの `.` は `_` にします）。
`stats.ys` の `mean` は `stats_mean` になります。

| 案 | 判断 |
|---|---|
| 関数名そのまま（`mean`） | ✗ `open` / `write` を出すと libc の同名の関数を**覆い隠し**、ランタイム自身の呼び出しがそちらへ行きます |
| **`モジュール名_関数名`** | **採用。** 読めて、libc と重なりにくく、2 つの実装で同じ名前になります |
| ハッシュを混ぜる | 読めません。C から呼ぶ人が困ります |

同じ名前が 2 つできたら（`a_b.ys` の `c` と `a.ys` の `b_c`）、**コンパイル時に断ります**（`E-EXPORT-5`）。

### 4.2 形

すべて同じ形です。**戻り値は状態、結果は最後の引数へ書きます。**

```c
// 0 = 成功（*out に結果）/ 1 = raises のエラー / 2 = panic
int64_t stats_mean(const double *xs, int64_t xs_len, double *out);
int64_t stats_greet(const char *name, int64_t name_len, int64_t times,
                    void **out);
int64_t stats_log(const char *const *xs, const int64_t *xs_lens, int64_t xs_len);
                    // ↑ list[str] は「先頭の並び・長さの並び・個数」。戻り値が None なら out は無い
```

- **失敗の中身**はスレッドごとに 1 つずつ持ち、次の関数で読みます。
  `pl_ffi_error_kind()`（エラーのクラス名。panic なら空）／`pl_ffi_error_message()`。
- **取っ手**（`str` / `list` の戻り値）は、読む関数と解放する関数を通して扱います：
  `pl_ffi_str_len` / `pl_ffi_str_data` / `pl_ffi_list_len` / `pl_ffi_list_data` /
  `pl_ffi_list_str_at` と、解放の `pl_ffi_free_str` / `pl_ffi_free_list` /
  `pl_ffi_free_list_str`。Python の生成コードは読んだら**すぐ写して解放**します。
- 既定引数は C には見えません（C からはすべて渡します）。Python の生成コードが補います。

注意: **`pl_` 以外の名前をランタイムに足しません。** 公開する口も `pl_ffi_` で
始まります（既存のランタイムと同じ規則です）。

## 5. 失敗の扱い

### 5.1 `raises` → Python の例外

`raises` した関数は、エラーのクラスごとに Python の例外クラスを生成します。

```python
class Error(Exception): ...          # このライブラリのエラーの共通の親
class EmptyError(Error): ...         # raises に書かれたクラスごとに 1 つ
```

- 例外の文面は、エラーのクラスに **`message: str` のフィールドがあれば**その中身、
  無ければクラス名です。
- エラーオブジェクトそのものは Python に渡しません（クラスは境界に出しません。§8）。境界で解放します。
- 別のモジュールに**同じ名前のエラークラス**があれば、Python では 1 つのクラスになります
  （見分ける手がかりがクラス名だけのため）。

### 5.2 `panic` → 境界で止める

範囲外アクセス・桁あふれ・0 除算・契約違反は `panic` です。
**いまはプロセスが終わります**（`pl_hook_panic` が `exit(1)` する）。
ライブラリの中でこれをすると、**Python ごと**（Jupyter ならカーネルごと）落ちます。

そこで、**外へ出す関数の入口でだけ**、C のランタイムが `setjmp` しておき、
`pl_hook_panic` はそこへ `longjmp` で戻ります。Python には `stats.Panic` という
例外が届きます（`Error` の子ではありません。§8.4 の「panic はバグ」を保つため）。

**★ これはアンワインドではありません。** 途中の枠の後始末（drop）は走らず、
その呼び出しで確保したメモリは**漏れます**。それでも安全だと言える理由が次節です。

### 5.3 なぜ安全だと言えるのか

`longjmp` で戻ったあと、壊れた状態が残らないことを示す必要があります。
残りうる場所は 3 つです。

| 残りうる場所 | 起きないと言える理由 |
|---|---|
| **その呼び出しの中の値** | 引数は写したもの（§3.1）で、Python からは見えません。捨てられるだけです（漏れる） |
| **グローバル変数** | 外へ出す関数は、呼び先までたどって**グローバルに書かない**ことを検査します（`E-EXPORT-3`）。書き換えの途中で止まることがありません |
| **動いているスレッド** | 外へ出す関数から **`spawn` と `scope:` に届かない**ことを検査します（`E-EXPORT-4`）。`scope:` の中のスレッドが、消えた枠を借りたまま動き続ける形を作らせません |

**★ `E-EXPORT-3` は `spawn` の `E-SEND-3` と同じ検査です。** 実は理由も同じです。
ctypes は呼び出しのあいだ GIL を手放すので、**Python の 2 つのスレッドが同じ関数を
同時に呼べます**。外へ出す関数は「どのスレッドから呼ばれるか分からない関数」で、
`spawn` で始める関数とまったく同じ立場です。グローバルに書かなければ、
**同時に呼ばれてもデータ競合がありません**（引数は呼び出しごとの写しなので）。

1 つの規則が、panic からの復帰と並行呼び出しの両方を守ります。

### 5.4 `sys.exit`

ライブラリの中から `sys.exit` を呼ぶと、Python ごと終わってしまいます。
入口に `setjmp` している間は、**`panic` と同じく `Panic` 例外に変えます**。

## 6. 生成物とコマンド

```console
$ yashirolang --shared stats.ys -o libstats.dylib   # C から使う共有ライブラリ
$ yashirolang --python stats.ys -o out/              # out/_stats.<拡張子> と out/stats.py
```

| | |
|---|---|
| `--shared` | `main` が要りません（あっても外には出しません）。`extern def`（本体つき）が 1 つも無ければエラー |
| `--python` | `--shared` と同じライブラリを `_<モジュール名>` で作り、隣に ctypes の .py を置きます |
| 共有ライブラリの拡張子 | macOS は `.dylib`、Linux は `.so`、Windows（MSYS2）は `.dll` |

### 6.1 なぜ ctypes なのか

| 案 | 判断 |
|---|---|
| **ctypes を使う .py を生成** | **採用。** Python の版ごとの ABI に縛られません（3.9 でも 3.13 でも同じ .so）。構築に `Python.h` が要らないので「clang だけで建つ」が保てます |
| Python の C API で拡張モジュールを作る | 呼び出しは少し速い。代わりに**版ごとに作り直し**になり、構築に Python の開発用ヘッダが要ります |
| cffi | 利用者に cffi を入れさせることになります |

呼び出し 1 回あたりの手間（ctypes の変換）は数百 ns 程度です。
**「小さい関数をたくさん呼ぶ」より「重い計算を 1 回呼ぶ」使い方**に向きます。

### 6.2 生成する .py の約束

- 型の検査は **Python 側の生成コードで先に**行います（C に渡る前に `TypeError`）
- 引数名・既定値は**元の宣言と同じ**です（キーワード引数で呼べます）
- 取っ手は読んだらすぐ写して解放します。Python 側に yashirolang の値は残りません
- 生成物に言語名は書きません（ファイル先頭の「生成しました」の一行だけ、langinfo から取ります）

## 7. 検査の一覧

| コード | 内容 |
|---|---|
| `E-EXPORT-1` | 境界に出せない型を、外へ出す関数の引数か戻り値に使っている（§3） |
| `E-EXPORT-2` | 外へ出す関数に `mut` 引数がある（写しを書き換えても外に戻らない） |
| `E-EXPORT-3` | 外へ出す関数が（呼び先までたどって）グローバルに書く |
| `E-EXPORT-4` | 外へ出す関数が（呼び先までたどって）`spawn` / `scope:` に届く（§5.3 の根拠なので外しません） |
| `E-EXPORT-5` | 外へ出す名前（`モジュール名_関数名`）が重なる |
| `E-EXPORT-6` | 本体つきの `extern` をクラスの中に書いた（メソッドは出せません） |

注意: **検査するのは `extern def`（本体つき）だけです。** ふつうの関数には何も
増えません。`--shared` / `--python` を付けないときも検査します（付けたかどうかで
通るかどうかが変わらないようにするため）。

## 8. 段階

**段階 1（この文書の §2〜§7）で完了です。** `int` / `float` / `bool` / `str` /
`list[int|float|bool|str]`、`raises`、panic の受け止め、`--shared` / `--python` までです。

段階 2・3 として予定していたものは、**安全を優先して入れないと決めました**。

| 入れないもの | 理由 |
|---|---|
| 外へ出す関数からの `spawn` / `scope:` | §5.3 の「動いているスレッドが残らない」が崩れます。panic したときのスレッドの待ち合わせと、`mutex` を持ったまま panic した場合の扱い（毒入り）という、**新しく示さなければならない保証**が増えます |
| `T | None` の引数と戻り値 | 危険は小さいものの、ABI と生成する .py に分岐が増えます。仕様を広げる理由になるほどの必要がありません |
| クラスを「取っ手」として外に見せる | **所有権が境界を越えます**（Python のオブジェクトが持ち主になり、`__del__` で解放する形）。所有権検査の外に持ち主ができます |
| `list[float]` を写さずに渡す（NumPy） | **借りが境界を越えます**。GIL を持ったまま呼ぶ・呼び出し中に書き換えない、という約束を Python 側に守ってもらうことになり、§3.1 の「写す」理由がそのまま当てはまります |

## 9. 保証していないこと

- **panic した呼び出しで確保したメモリは解放されません**（§5.2）。panic はバグなので、
  たくさん起きる前提にはしていません
- **`print` の出力順**。yashirolang の `print` は C の `stdout` に、Python の `print` は
  `sys.stdout` に書くので、混ぜると順序が入れ替わることがあります
- **`unsafe:` の中身**。外へ出す関数から届く `unsafe:` は、いままでどおり保証の外です
- **Windows の DLL の配置**。隣の `.dll` を読む前提です（`os.add_dll_directory` は生成コードが呼びます）
- **関数ポインタ・インタフェース越しの呼び出しの先**。`E-EXPORT-3` / `E-EXPORT-4` は呼び先を
  名前でたどるので、値として渡された関数の中までは見ません（`spawn` の `E-SEND-3` と同じ限界です）
