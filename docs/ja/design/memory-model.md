# メモリモデル

> 「値はどこに置かれ、いつ消えるのか」を定義します。

---

## 1. 値の分類：値型と参照型

| 分類 | 型 | 変数が保持するもの | 代入の意味 |
|---|---|---|---|
| **値型** | `int`, `float`, `bool` | 値そのもの | 値をコピー |
| **参照型** | `str`, `list[T]`, `dict[K,V]`, class | ヒープ上のオブジェクトへのポインタ | ポインタをコピー |

Python と同じ**参照セマンティクス**です。

```python
a: list[int] = []
a.append(1)
b: list[int] = a      # b と a は同じリストを指す
b.append(2)
print(len(a))          # 2 （a も変わる）
```

```
  a ──┐
      ├──▶ [ptr | len=2 | cap=4] ──▶ [1][2][ ][ ]
  b ──┘
```

**注意: `str` は参照型だが不変（immutable）です。**
`s = s + "a"` は新しい文字列を作って `s` を差し替えます。元の文字列は変更されません。
不変なので、参照を共有していても値が勝手に変わる心配がありません。

## 2. 格納場所

```
┌───────────────────────────────────────────────┐
│ .rodata（読み取り専用データ）                    │
│   文字列リテラル @.str.0 など                    │  ← プログラム終了まで存在
├───────────────────────────────────────────────┤
│ .data / .bss（グローバル変数）                   │
│   @g.counter など                              │  ← プログラム終了まで存在
├───────────────────────────────────────────────┤
│ ヒープ（malloc）                                │
│   class インスタンス、list の本体、               │  ← v2: 所有者が解放する
│   実行時に作った文字列                            │
├───────────────────────────────────────────────┤
│         ↓ 伸びる                               │
│                                               │
│         ↑ 伸びる                               │
│ スタック（alloca）                              │
│   ローカル変数の「箱」                            │  ← 関数から抜けると消える
└───────────────────────────────────────────────┘
```

### 最重要の注意：スタックのアドレスを返してはいけない

```python
class Point:
    x: int
    y: int

def make() -> Point:
    p: Point = Point(1, 2)
    return p          # OK
```

これが安全なのは、`Point(1, 2)` が**ヒープに**確保されるからです。
ローカル変数 `p`（`alloca` されたスタック上の箱）が保持しているのは
ヒープへのポインタであり、返るのはそのポインタです。

```
スタック                ヒープ
┌──────────┐
│ %p: ptr  │────────▶ ┌────────────┐
└──────────┘          │ x=1, y=2   │
   ↑ 関数から抜けると消える  └────────────┘
                          ↑ 残る（返り値として有効）
```

> **すべてのユーザー定義オブジェクトを常にヒープに確保する**という規則にすることで、
> 「スタックのアドレスを返してしまう」バグを**構造的に不可能**にしています。

**なぜスタック確保（値型の struct）を用意しないのか**
C や Rust のように構造体をスタックに置けると高速ですが、
「エスケープ解析」（そのオブジェクトが関数の外に漏れるかの判定）が必要になります。
これは最適化の話題であり、v1 のスコープ外です。

## 3. メモリ解放：所有者のスコープ終端で解放する

> **★ 既定で解放します**（0.16.0 から）。所有権検査で「誰が所有者か」が
> 静的に決まるので、**所有者のスコープが終わるときに解放**します。
> 挿入するのは codegen で、規則は [ownership.md §6](ownership.md) にあります。
>
> | | 扱い |
> |---|---|
> | 解放 | **所有者のスコープ終端で解放する** |
> | 誰が決めるか | 所有権検査（ownck）が「所有者かどうか」を決める |
> | 移動した値 | スロットに `null` を書いてあるので解放されない（§6.3） |
> | 借りもの | **解放しない**（引数・`for` の要素・`self` の借用の返却） |
> | 文字列リテラル | 解放しない（ヘッダの「静的」ビットで見分ける） |
> | 打ち消し | `--no-drop`（診断を見せるときなど。ふつうは使いません） |
>
> **注意: 以下は `--no-drop` を付けたときの動作です**（解放が既定になる前の挙動でもあります）。

**`--no-drop` では `free()` を一切呼びません。**

```llvm
%t0 = call ptr @malloc(i64 16)
; free は呼ばない
```

### なぜそれで許されるのか

1. **主なターゲットが短命プロセスである**
   この言語の第一の用途は「yashirolang コンパイラ自身を書くこと」です。
   コンパイラは 1 ファイルを処理して終了します。プロセス終了時に OS が全ページを回収します。

2. **メモリ管理は独立した大プロジェクトである**
   - 手動 `free` → 言語に所有権の概念が必要。二重解放・use-after-free のバグ地獄
   - 参照カウント → すべての代入にカウンタ操作の挿入。循環参照の問題
   - トレース GC → ルート集合の把握、スタックスキャン、`safepoint` の挿入…

   どれも「言語を作る」より大きな仕事です。セルフホストに到達できなくなります。

3. **実際に足りる**
   yashirolang コンパイラのソースが 1 万行、AST ノードが 10 万個できたとしても、
   1 ノード 150 バイトで 15MB です。現代の機械では問題になりません。

### 許されない用途

- 長時間動くサーバ
- ループの中で大量にオブジェクトを作り続けるプログラム

これらは v1 の想定外です。**仕様上の既知の制限**として明記します。

### 将来の選択肢（v2 以降）

| 方式 | 難易度 | 備考 |
|---|---|---|
| **アリーナ（領域）確保** | ★ | 大きなブロックを確保し、そこから切り出す。`arena_reset()` で一括解放。**次に採用するならこれ** |
| 参照カウント | ★★★ | 循環参照が漏れる。代入のたびにコード挿入 |
| マーク&スイープ GC | ★★★★ | スタックスキャンが必要。移植性が低い |
| 所有権（Rust 風） | ★★★★★ | 型システムの大改造 |

アリーナは実装が 50 行程度で、`malloc` の呼び出し回数を劇的に減らせるため
**性能改善としても価値があります**。セルフホスト後の課題とします。

## 4. ランタイムの確保 API

`runtime/runtime.c` が提供する確保関数です。

```c
// メモリ確保（失敗したら異常終了する）
void *pl_alloc(long long size);

// 文字列（★「長さ付き」。[i64 長さ][バイト列][NUL] で、
//         値が指すのはバイト列の先頭。詳細は ir-conventions.md 8.1）
char *pl_str_alloc(long long len);                   // 長さ付きの器を確保する
char *pl_str_from_cstr(const char *s);               // C 文字列から作る
char *pl_str_concat(const char *a, const char *b);   // 新しい文字列を作る
long long pl_str_len(const char *s);                 // O(1)
long long pl_byte_at(const char *s, long long i);    // 確保しないバイトアクセス
char *pl_str_join(PlList *xs, const char *sep);      // O(n) の連結
int  pl_str_eq(const char *a, const char *b);
char *pl_str_from_int(long long n);
char *pl_str_sub(const char *s, long long start, long long len);

// リスト
typedef struct { void *data; long long len; long long cap; } PlList;
PlList *pl_list_new(long long elem_size);
void    pl_list_push_i64(PlList *l, long long v);
void    pl_list_push_ptr(PlList *l, void *v);
long long pl_list_get_i64(PlList *l, long long i);   // 範囲検査あり
void   *pl_list_get_ptr(PlList *l, long long i);
long long pl_list_len(PlList *l);
```

### `pl_alloc` はなぜ `malloc` を直に使わないのか

```c
void *pl_alloc(long long size) {
    void *p = calloc(1, (size_t)size);
    if (!p) {
        fputs("runtime error: out of memory\n", stderr);
        exit(1);
    }
    return p;
}
```

- **`calloc` でゼロ初期化**する → フィールド未初期化による不定値バグを防ぐ
- **失敗時に即終了**する → 生成する IR に NULL チェックを入れなくて済む（IR が単純になる）

> **生成される IR を単純に保つために、複雑さをランタイムの C 側に押し出す。**
> これは [ir-conventions.md](ir-conventions.md) の R10 と同じ思想です。

## 5. アラインメントとサイズ

C の規則をそのまま採用します。

| 型 | サイズ | アラインメント |
|---|---|---|
| `int` | 8 | 8 |
| `float` | 8 | 8 |
| `bool` | 1 | 1 |
| `str` | 8 | 8 |
| `list[T]` | 8 | 8 |
| class（参照） | 8 | 8 |

クラスの実体のサイズは、フィールドを宣言順に並べてパディングを入れて計算します。

```python
class Mixed:
    a: bool     # offset 0, size 1
    b: int      # offset 8, size 8  ← 7 バイトのパディングが入る
    c: bool     # offset 16, size 1
                # 全体サイズ: 24（アラインメント 8 に切り上げ）
```

```llvm
%Mixed.type = type { i8, i64, i8 }
```

**注意: LLVM は構造体のパディングを自動で計算します。**
`%Mixed.type` に対する `getelementptr` は正しいオフセットを出してくれるので、
**フィールドアクセスのために自分でオフセット計算をする必要はありません。**

自分でサイズ計算が必要になるのは `malloc` に渡すバイト数だけです。
それも LLVM に計算させる手があります。

```llvm
; sizeof(%Mixed.type) を LLVM に計算させる定番のイディオム
; 「NULL から 1 個分進めたアドレス」＝サイズ
%size_ptr = getelementptr %Mixed.type, ptr null, i32 1
%size = ptrtoint ptr %size_ptr to i64
%obj = call ptr @pl_alloc(i64 %size)
```

**どちらを使うべきか**
この教材では **コンパイラ側で計算する方式**を採用します。

- 理由 1: 型検査でどうせフィールドのオフセットは必要（`getelementptr` のインデックス決定）
- 理由 2: `sizeof` イディオムは初見で意味が読めず、教材として不親切
- 理由 3: 自分で計算すればアラインメント規則を理解できる

ただしイディオムを知っていると、パディング計算のバグを検証するのに使えます。
**両方を計算して一致するか確認する**テストを書くと安心です。

## 6. 初期化の保証

> **すべての変数は宣言時に初期化される。未初期化変数は存在しない。**

これは言語仕様（[../spec/language-spec.md](../spec/language-spec.md) 5.1）で
`x: int` だけの宣言を禁止し、`x: int = 0` を必須にしていることで保証されます。

| 対象 | 初期化 |
|---|---|
| ローカル変数 | ソースで初期化式が必須 |
| グローバル変数 | ソースで初期化式が必須（コンパイル時定数） |
| クラスのフィールド | `pl_alloc` の `calloc` により 0 / NULL |
| `list` の未使用容量 | `calloc` により 0 |

**注意: クラスのフィールドについての注意**
`init` メソッドでフィールドを設定し忘れると、値は 0 / NULL になります。
これは「不定値」ではないので**再現性のあるバグ**になり、デバッグ可能です。

「全フィールドが `init` で代入されているか」の検査は v1 では行いません（将来の課題）。

## 7. None（null ポインタ）

`None` は**アドレス 0（null ポインタ）**として表現します。

```llvm
store ptr null, ptr %t          ; t = None
%t0 = load ptr, ptr %t
%t1 = icmp eq ptr %t0, null     ; t is None
```

型システムが `T | None` でないところに `None` が入るのを防ぐので、
**型検査を通ったコードで null 参照は起きない**のが理想です。

ただし第6節のとおり、クラスのフィールドは `calloc` により NULL から始まります。
そのため：

- `T | None` 型のフィールド → 正しく `None` として扱われる - `T` 型（non-null）のフィールドを `init` で設定し忘れた → **NULL 参照になる** 注意: **この穴は 0.18.0 で塞ぎました**（A-27）。`init` の**どの経路でも**
代入するかを見ます（Ada / SPARK の definite assignment にあたる検査）。
`if` の中にしか代入が無い形も、代入の前に `return` する経路も止まります。

注意: **それでもランタイムの NULL 検査は残します。** 静的に見られるのは
`init` の中だけで、**代入の前に読む**形（`print(self.f.v)` を書いてから
`self.f = ...` する）までは面倒を見られないためです。

```llvm
call void @pl_check_not_none(ptr %t0)      ; NULL なら親切に死ぬ
%t1 = getelementptr %Token.type, ptr %t0, i32 0, i32 0
```

**注意: このチェックは `-O2` でも消えません**（副作用があるため）。
性能が問題になったら `--no-null-checks` フラグで無効化できるようにします。

## 8. コンパイラ自身のメモリ管理

`yashirolang`（C 版）も同じ方針です。

```c
void *xmalloc(size_t n) {
    void *p = calloc(1, n);
    if (!p) error("メモリ確保に失敗しました");
    return p;
}
```

`free()` は書きません。理由は第3節と同じです。

**注意: 所有権検査が挿入する `free()` は「利用者のプログラム」の側です。**
コンパイラ自身（`src/` と `selfhost/`）は、今も確保しっぱなしで動いています。
混同しないこと：解放するのは **ランタイム（`runtime/runtime.c`）** と、
そこを呼ぶ **生成された IR** です。

**この一貫性には実用的な意味があります。**
C 版とセルフホスト版で同じメモリ戦略を採ることで、セルフホストへの移植で
「C 版では free していたが yashirolang には free がない」という食い違いが起きません。

## 9. まとめ

| 問い | 答え |
|---|---|
| `int` はどこにある？ | ローカルならスタック（alloca）、グローバルなら .data |
| `list` の中身はどこ？ | ヒープ |
| class のインスタンスはどこ？ | 常にヒープ |
| 文字列リテラルはどこ？ | .rodata（読み取り専用） |
| 実行時に作った文字列はどこ？ | ヒープ |
| いつ解放される？ | **プロセス終了時（明示的な解放はしない）** |
| 代入はコピーか参照か？ | 値型はコピー、参照型はポインタのコピー |
| 未初期化変数はある？ | ない（宣言時の初期化を文法で強制） |
| `None` の表現は？ | null ポインタ（アドレス 0） |
