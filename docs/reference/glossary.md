## コンパイラの全体構造

### コンパイラ (compiler)
ソースコードを別の形式（機械語や別の言語）に**翻訳する**プログラム。
実行はしない。翻訳するだけ。

### インタプリタ (interpreter)
ソースコードを翻訳せずに**その場で実行する**プログラム。Python は通常こちら。

### トランスパイラ (transpiler)
高級言語から高級言語へ翻訳するコンパイラ。TypeScript → JavaScript など。

### パス (pass)
コンパイラの中の 1 段階。本言語では
「字句解析 → 構文解析 → 意味解析 → コード生成」の 4 パス。

### フロントエンド / バックエンド
- **フロントエンド**：ソース言語に依存する部分（字句解析〜意味解析）。**私たちが書く**
- **バックエンド**：ターゲット機械に依存する部分（機械語生成、レジスタ割り当て、最適化）。**LLVM に任せる**

### 中間表現 (IR: Intermediate Representation)
フロントエンドとバックエンドの間でやり取りされるデータ形式。**LLVM IR** がそれ。

## 字句解析

### 字句解析 (lexical analysis) / 字句解析器 (lexer, tokenizer, scanner)
**文字の並び**を**トークンの並び**に変換する処理・プログラム。

```
"x = 1 + 2"  →  [IDENT(x)] [=] [INT(1)] [+] [INT(2)]
```

### トークン (token)
言語の最小単位。「単語」に相当する。
種類（kind）と、必要なら値（数値、文字列など）と、位置情報を持つ。

### リテラル (literal)
ソースコードに直接書かれた値。`42`, `"hello"`, `True` など。

### キーワード (keyword) / 予約語 (reserved word)
言語が意味を定めている単語。`if`, `def`, `return` など。識別子として使えない。

### 識別子 (identifier)
プログラマが付けた名前。変数名・関数名・クラス名。

### オフサイドルール (off-side rule)
**インデント（字下げ）でブロック構造を表す**方式。Python と本言語が採用。
対比されるのは波括弧 `{}` でブロックを表す方式（C, Java）。

### INDENT / DEDENT
オフサイドルールを実装するために、**字句解析器が合成する仮想トークン**。
ソースコード中に対応する文字がない。波括弧言語の `{` `}` の役割を果たす。

### 論理行 / 物理行
- **物理行**：ファイル中の改行で区切られた 1 行
- **論理行**：文法上の 1 行。括弧の中では複数の物理行が 1 論理行になる

### 先読み (lookahead)
次のトークン（または文字）を、消費せずに覗くこと。
`peek()` と `next()` の違い：`peek` は覗くだけ、`next` は消費して進む。

## 構文解析

### 構文解析 (syntactic analysis, parsing) / 構文解析器 (parser)
**トークンの並び**を**構文木**に変換する処理・プログラム。

### 構文木 / 抽象構文木 (AST: Abstract Syntax Tree)
プログラムの構造を木として表したもの。

```
1 + 2 * 3       →        +
                        / \
                       1   *
                          / \
                         2   3
```

**「抽象」の意味**：括弧やセミコロンなど、構造が決まれば不要になる情報を捨てている。
`(1 + 2)` と `1 + 2` は同じ AST になる。

### 具象構文木 (CST: Concrete Syntax Tree) / パースツリー
括弧やスペースまで含めて全部保持する木。IDE やフォーマッタが使う。
**コンパイラには AST で十分。**

### 文法 (grammar)
言語の構造を定める規則の集合。→ [spec/grammar.md](../spec/grammar.md)

### EBNF (Extended Backus-Naur Form)
文法を書き表すための記法。`A ::= B { C }` のように書く。

### 終端記号 / 非終端記号
- **終端記号 (terminal)**：それ以上分解されないもの。トークン
- **非終端記号 (nonterminal)**：他の記号に展開される規則名。`expr`, `stmt` など

### 再帰下降構文解析 (recursive descent parsing)
**文法規則 1 つを関数 1 つに対応させて、上から下へ再帰的に降りていく**手法。
手書きで最も書きやすく、エラーメッセージを作りやすい。**この教材で使う方式。**

```
expr()  →  add_expr()  →  mul_expr()  →  unary()  →  primary()
```

### LL(1) / LL(k)
「左から読み、左端導出、k トークン先読み」で解析できる文法のクラス。
再帰下降で素直に書けるのはこの範囲。本言語の文法はほぼ LL(2)（`x : int` の判別で 2 個必要）。

### LR / LALR
別系統の構文解析手法。yacc / bison が生成するのはこれ。
より広い文法を扱えるが、**エラーメッセージが作りにくく、手書きに向かない**。

### パーサジェネレータ (parser generator)
文法定義からパーサのコードを自動生成するツール。yacc, bison, ANTLR など。
**この教材では使いません**（何が起きているか見えなくなるため）。

### 演算子の優先順位 (precedence)
`1 + 2 * 3` で `*` を先に計算するという規則。
再帰下降では**関数の呼び出し階層の深さ**で表現する。→ [spec/grammar.md](../spec/grammar.md) 第5節

### 結合性 (associativity)
同じ優先順位の演算子が並んだときの結合方向。
- **左結合**：`1-2-3` → `(1-2)-3`。ほとんどの演算子
- **右結合**：`2**3**4` → `2**(3**4)`。べき乗、代入

### 脱糖 (desugaring)
構文糖（便利な書き方）を、基本的な構文に書き換えること。
本言語では `for` を `while` に、`elif` を `else: if` に、`x += 1` を `x = x + 1` に脱糖する。

### 構文糖 (syntactic sugar)
なくても同じことが書けるが、あると便利な構文。

## 意味解析・型

### 意味解析 (semantic analysis)
構文的には正しいプログラムについて、**意味が通るか**を検査する処理。
型検査、名前解決、到達可能性検査などを含む。

### 型検査 (type checking) / 型検査器 (type checker)
式や変数の型が整合しているか検査する処理。→ [spec/type-system.md](../spec/type-system.md)

### 静的型付け / 動的型付け
- **静的 (static)**：**コンパイル時**に型が決まる。本言語, C, Java
- **動的 (dynamic)**：**実行時**に型が決まる。Python, Ruby, JavaScript

### 型推論 (type inference)
型注釈なしに型を推測すること。`x = 0` から `x: int` を導く。
**本言語 v1 では行いません**（型注釈を必須にすることで実装を単純化）。

### 型注釈 (type annotation)
ソースコードに明示的に書かれた型。`x: int` の `: int` の部分。

### 健全性 (soundness)
「型検査を通ったプログラムは実行時型エラーを起こさない」という性質。
型システムの目標。

### 名前解決 (name resolution)
識別子が**どの宣言を指すか**を決めること。
`x` という参照を、どの `x: int = ...` に結びつけるか。

### シンボルテーブル (symbol table)
「名前 → 宣言情報（型、格納場所など）」の対応表。

### スコープ (scope)
名前が有効な範囲。本言語ではグローバル / 関数 / ブロックの 3 種類。

### シャドーイング (shadowing)
内側のスコープで外側と同名の変数を宣言し、外側を隠すこと。
**本言語 v1 では禁止**（混乱を避けるため）。

### 環境 (environment) / Γ（ガンマ）
型付け規則の説明で使われる「名前 → 型」の対応。実装上はシンボルテーブル。

### 双方向型検査 (bidirectional type checking)
「式から型を求める（合成）」と「期待される型を式に伝える（検査）」を組み合わせる手法。
空リスト `[]` の型を文脈から決めるのに使う。

### 型の絞り込み (narrowing)
`if t is not None:` の中では `t` の型が `Token | None` から `Token` に絞られる、という処理。

### 部分型 (subtyping)
「A 型は B 型としても使える」という関係。継承がある言語で必要。
**本言語 v1 にはありません**（`T` → `T | None` のみ例外）。

### 不変 / 共変 / 反変 (invariant / covariant / contravariant)
ジェネリック型の部分型関係の向き。本言語の `list[T]` は**不変**（`list[int]` と `list[str]` は無関係）。

## コード生成

### コード生成 (code generation) / コード生成器 (codegen)
AST から目的の出力（本言語では LLVM IR テキスト）を作る処理・プログラム。

### SSA (Static Single Assignment) 形式
**各レジスタに 1 回しか代入しない**中間表現の形式。LLVM IR がこれ。
最適化がしやすくなる。

```llvm
%x = add i64 1, 0
%x = add i64 2, 0    ; ✗ SSA 違反
```

### phi 命令 (φ, phi node)
SSA で「**どのブロックから来たかによって値を選ぶ**」命令。
分岐が合流する地点で必要になる。

```llvm
%x.3 = phi i64 [ %x.1, %then ], [ %x.2, %else ]
```

**この教材では自分で生成しません。** 全変数を `alloca` に置き、LLVM の `mem2reg` に任せる。

### alloca
スタック上にメモリを確保する LLVM 命令。
**本言語のローカル変数はすべてこれで表現する。** → [design/ir-conventions.md](../design/ir-conventions.md) 第1節

### mem2reg
`alloca` / `load` / `store` を SSA レジスタと `phi` に変換する LLVM の最適化パス。
**この教材の設計を成立させている鍵。**

### 基本ブロック (basic block)
**分岐を含まず、上から下へ一直線に実行される命令の並び**。
必ず 1 つの終端命令で終わる。

### 終端命令 (terminator instruction)
基本ブロックを終わらせる命令。`ret`, `br`, `switch`, `unreachable`。
**すべての基本ブロックはこれで終わらなければならない。**（最頻出の落とし穴）

### 制御フローグラフ (CFG: Control Flow Graph)
基本ブロックをノード、分岐をエッジとする有向グラフ。プログラムの実行経路を表す。

### 到達不能コード (unreachable code)
どの経路からも実行されないコード。`return` の直後など。
IR ではラベルと `unreachable` 命令が必要になる。

### getelementptr (GEP)
**アドレス計算だけを行う** LLVM 命令。メモリアクセスはしない。
構造体のフィールドや配列の要素のアドレスを求める。

### opaque pointer
LLVM 15（2022）以降、ポインタ型が指す先の型情報を持たなくなったこと。
すべて `ptr` と書く。`i8*` や `i64*` は使えない。

### 名前修飾 (name mangling)
同名の関数が衝突しないように、名前を機械的に加工すること。
本言語では `Token.is_eof` → `@Token.is_eof`、モジュール内なら `@lexer.tokenize`。

### 呼び出し規約 (calling convention)
引数をどこに置き、戻り値をどう返すかの取り決め。
**LLVM が処理するので、私たちは意識しません。**

### 即値 (immediate)
命令のオペランドに直接書かれた定数。`add i64 %t0, 1` の `1`。

### 一時値 (temporary)
式の中間結果を保持するレジスタ。`%t0`, `%t1` など。

## 最適化

### 最適化 (optimization)
プログラムの意味を変えずに、速度やサイズを改善すること。
**この教材では LLVM に任せます。**

### 定数畳み込み (constant folding)
コンパイル時に計算できる式を計算してしまうこと。`2 * 3` → `6`。

### 不要コード削除 (DCE: Dead Code Elimination)
結果が使われない計算を削除すること。

### インライン展開 (inlining)
関数呼び出しを、その関数の本体で置き換えること。

### レジスタ割り当て (register allocation)
値を CPU の物理レジスタに割り当てること。**LLVM のバックエンドの仕事。**

## セルフホスト

### ブートストラップ (bootstrapping)
「コンパイラを書くにはコンパイラが必要」という循環を、
**別の既存コンパイラを踏み台にして**解決する手法。

### セルフホスト (self-hosting)
コンパイラが**自分自身のソースコードをコンパイルできる**状態。
→ [design/self-hosting.md](../design/self-hosting.md)

### stage0 / stage1 / stage2
ブートストラップの各段階のコンパイラ。
- **stage0**：C で書かれ、外部の clang でビルドされたもの
- **stage1**：本言語で書かれ、stage0 でビルドされたもの
- **stage2**：本言語で書かれ、stage1 でビルドされたもの

### 不動点 (fixed point)
`f(x) == x` となる `x`。ブートストラップでは
**「stage2 と stage3 が一致する」= セルフホスト成功**の判定基準。

**なぜ stage1 と stage2 は一致しなくてよいのか**は
[design/self-hosting.md](../design/self-hosting.md) 第2節で詳しく説明しています。

### クロスコンパイル (cross compilation)
動作している機械とは別のアーキテクチャ向けの機械語を生成すること。

## メモリ

### スタック (stack)
関数呼び出しごとに伸縮する領域。ローカル変数の置き場所。
**関数から抜けると無効になる。**

### ヒープ (heap)
`malloc` で確保する領域。**明示的に解放するまで有効。**
本言語のオブジェクト（class, list, 実行時の文字列）はここ。

### 値型 / 参照型
- **値型**：変数が値そのものを持つ。`int`, `float`, `bool`
- **参照型**：変数がポインタを持つ。`str`, `list`, class

### 不変 (immutable)
作った後に変更できないこと。本言語の `str` は不変。

### ガベージコレクション (GC)
不要になったヒープ領域を自動的に回収する仕組み。
**本言語 v1 にはありません。** → [design/memory-model.md](../design/memory-model.md)

### アリーナ (arena) / 領域確保 (region allocation)
大きなブロックをまとめて確保し、そこから切り出す方式。
一括で解放できる。**v2 で採用予定。**

### アラインメント (alignment)
値がメモリ上で配置されるべき境界。`i64` は 8 バイト境界。

### パディング (padding)
アラインメントを満たすために構造体に挿入される未使用バイト。

### NUL 終端 (NUL-terminated)
文字列の終わりをバイト値 0 で示す方式。C と本言語 v1 の `str` がこれ。

## テスト・開発

### 回帰テスト (regression test)
「以前動いていたものが壊れていないか」を確認するテスト。
**各章でテストを足していくのが、この教材の進め方の核心。**

### ゴールデンテスト (golden test) / スナップショットテスト
期待される出力を保存しておき、それと比較するテスト。
`--dump-ast` の出力比較がこれ。

### AddressSanitizer (ASan)
メモリバグ（範囲外アクセス、use-after-free）を実行時に検出する clang の機能。
**コンパイラ開発では必須の道具。**

### インクリメンタル開発 (incremental development)
**常に動く状態を保ちながら**少しずつ機能を足す進め方。
この教材の基本方針。
