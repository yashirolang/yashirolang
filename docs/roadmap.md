## 0. この言語が譲らないこと

**目標は「世界一安全な言語」です。ただし Python の書きやすさは絶対です。**

この 2 つは衝突します。安全性を上げようとすると注釈が増え、書きやすさを
上げようとすると検査が緩みます。**どちらを取るかは、次の順で決めます。**

### ① 書きやすさが下がるなら、その安全機能は入れない

| 入れないもの | なぜ |
|---|---|
| ライフタイム注釈（`'a`） | 型注釈以外の注釈を増やさない。借用は「呼び出しより長生きしない」規則で代用する |
| 呼び出し側の印（`&x` / `x.clone()`） | 呼ぶたびに書かせない。`own` / `mut` は**定義側に 1 回**だけ |
| 明示的な型引数（`f::<int>(x)`） | 実引数と左辺から推論する。書けないなら**その機能を入れない** |
| 検査を通すためだけの書き換え | 「コンパイラを黙らせる作法」を覚えさせない |

### ② 安全性が下がるなら、その書きやすさは入れない

| 入れないもの | なぜ |
|---|---|
| 暗黙の型変換 | `int` と `float` すら混ぜない。どこで精度が落ちたか追えなくなる |
| `null` を返す標準関数 | 「無い」は `T \| None` で型に出す。使う前に必ず確認させる |
| 例外の暗黙伝播 | `raises` に書いていないものは投げられない。握りつぶせない |
| truthiness（`if xs:`） | 「空か」と「None か」を取り違える |

### ③ 両立できないときは、**書きやすい側を採って、安全性は別の手段で取り戻す**

これが実際に効いた例です。

| 場面 | 採った書きやすさ | 取り戻した安全性 |
|---|---|---|
| 所有権の検査 | 既定は**警告**。既存コードがそのまま動く | `--deny-*` で段階的にエラーへ上げられる |
| ジェネリクス | 型制約を書かせない | 実体化したときに検査し、**発端の行**を示す |
| インタフェース | クラス→インタフェースの変換を書かせない | vtable をオブジェクトに埋め、変換自体を無くす |
| `float` | `1.5` と書ける | `int` との混在は**必ずエラー**にする |

### 安全性の現在地

| 保証していること | どう保証するか |
|---|---|
| null 参照が無い | `T \| None` と絞り込み（`is not None`） |
| 未初期化の読み出しが無い | 宣言に初期化式が必須 |
| 範囲外アクセスで壊れない | 実行時に検査して `panic`（黙って隣を読まない） |
| 型の取り違えが無い | 静的型付け・暗黙変換なし |
| 握りつぶされたエラーが無い | `raises` は `try` か再宣言のどちらかを強制 |
| 二重解放・解放後の使用が無い | 所有権・借用・可変性の検査（⚠️ 既定は警告） |
| データ競合が無い | **`spawn` に渡せるのは `own` した値か `mutex[T]` だけ**。借用と `rc[T]` は渡せません（`E-SEND-1` / `E-SEND-2`）。スレッドからのグローバル書き換えも止めます（`E-SEND-3`。⚠️ 呼び先まで**たどって**探します） |

| **整数があふれない** | `+` `-` `*` `**` と単項 `-`、`int(float)` / `int(str)` を検査。折り返したいときは `wrap_*`。⚠️ 添字の中の算術は**範囲検査に相乗り**させます（止まることは同じで、診断が「添字の計算があふれた」になります） |
| **0 で割れない**（整数も float も） | `a // 0` `a % 0` に加え、**`x / 0.0` も実行時エラー**。無限大が欲しいときは `math.inf()` |

### Rust / Ada と比べてどのぐらいか

**答え：「Rust に近いが、既定の強制力が弱い。Ada/SPARK には届いていない」**です。
気持ちの良い言い方をしても仕方がないので、項目ごとに並べます。

| 保証 | 本言語 | Rust | Ada / SPARK |
|---|---|---|---|
| null 参照が無い | ✅ `T \| None` と絞り込み | ✅ `Option` | ⚠️ 既定では無い（`not null` は付けられる） |
| 未初期化の読み出しが無い | ✅ 初期化式が必須 | ✅ | ⚠️ 既定では無い（SPARK は ✅） |
| 範囲外アクセスで壊れない | ✅ 実行時検査（**外せません**） | ✅ | ✅ |
| 暗黙の型変換が無い | ✅ `int`/`float` すら混ぜない | ✅ | ✅（さらに強い） |
| 握りつぶされたエラーが無い | ✅ `raises` は `try` か再宣言 | ✅ `Result` + `must_use` | ⚠️ 例外は握りつぶせる |
| **整数があふれない** | ✅ **常に検査**（外すのは `--no-overflow-check`） | ⚠️ **debug のみ**（release は折り返す） | ✅ 常に検査 |
| 二重解放・解放後の使用が無い | ⚠️ **既定は警告**（`--deny-*` でエラー） | ✅ **常にエラー** | ✅（そもそも所有権が無く GC も無い設計） |
| データ競合が無い | ✅ **`E-SEND-*`**（⚠️ **注釈は 1 つも増えません** — 所有権検査が既に持っている情報だけで判定します） | ✅ `Send`/`Sync`（トレイトを型に付けて回す） | ✅ Ravenscar |
| float の 0 除算 | ✅ **実行時エラー** | ❌ `inf` | ✅ `Constraint_Error` |
| 値の範囲を型で縛る | ❌ | ❌ | ✅ **部分型**（`range 0..100`） |
| 事前条件・事後条件・証明 | ❌ | ❌ | ✅ **SPARK** |
| 逃げ道 | `unsafe:` | `unsafe` | `Unchecked_*` |

#### いちばん大きな差は 3 つです

1. **所有権の検査が既定では警告です。** 仕組み自体は Rust と同じことを見ていて、
   `--deny-move --deny-borrow --deny-mut` を付ければエラーになります
   （**コンパイラ自身がその状態で通ります**）。
   ですが「既定で通ってしまう」以上、Rust と同じ強さだとは言えません。
   これは[§0 ③](#③-両立できないときは書きやすい側を採って安全性は別の手段で取り戻す)で
   意図して選んだ折衷です。
2. **✅ 埋まりました。** `spawn` / `join` / `mutex[T]` と、
   送出可能性の検査（`E-SEND-1`〜`3`）が入りました。**利用者が書く注釈は
   1 つも増えていません** — 借りか、所有か、`rc` か、という所有権検査が
   すでに持っている情報だけで判定しているためです。
   さらに **`spawn` を使ったファイルでは所有権検査が自動でエラーに上がる**ので、
   1 の「既定は警告」の弱さも、並行実行を使う場所では効きません。
   ⚠️ 残っている穴は「読み取りの共有ができない」ことです
   （[設計 §4.1](design/concurrency.md)）。
3. **Ada の部分型と SPARK の証明にあたるものがありません。**
   「0〜100 しか入らない整数」を型で言えません。実行時 `assert` で書きます。

#### 逆に本言語のほうが強いところ

- **整数のオーバーフローを、最適化しても検査します。** Rust の release ビルドは
  黙って折り返します。ここは Ada 側の設計を採りました。
- **範囲検査を外す手段を用意していません。** `--no-overflow-check` でも
  添字の検査は残ります。
- **`float(str)` や `int(str)` が読めない文字列を黙って 0 にしません**。

### 書きやすさの現在地

**Python の 1.7 倍の行数**、というのが実測です。

同じ処理（CSV を読む → 集計 → 2 枚の図 → 最大値の報告）を書き比べました
（[examples/sales_report{{ext}}](../examples/sales_report{{ext}}) と pandas + matplotlib）。

| | 行数（コメント・空行を除く） |
|---|---|
| Python（pandas + matplotlib） | **30 行** |
| 本言語 | **52 行** |

**差の内訳**は、型注釈（15 か所）と、次の「まだ無いもの」です。

| 無いもの | 何行ぶんか | 代わり |
|---|---|---|
| 書式指定（`f"{x:>8.2f}"`） | 数行 | `strings.lpad` / `math.round_to` |
| 既定引数・キーワード引数 | 数行 | 引数を全部書く |
| `lambda` / 内包表記の入れ子 | 数行 | `def` を切り出す |
| 数値の列での `group_by` | — | ✅ 入れました |

⚠️ **ライフタイム注釈も `&` も `.clone()` も要りません。** Rust と比べたときの
書きやすさは、ここで効いています。`own` / `mut` は**定義側に 1 回**だけです。

### 保証していないこと

| 穴 | 実際に起きること |
|---|---|

| **`--no-overflow-check` を付けたとき** | 整数の桁あふれは検査されません（速さのための逃げ道） |
| コンパイラ自身が検査を通らない | 下記 |

✅ **いちばん大きな穴だった「コンパイラ自身が検査を通らない」は埋まりました**
（345 → 0 件。`make own-strict` で確かめられます）。

✅ **並行実行とデータ競合の検査も入りました**（`spawn` / `mutex[T]` と
`E-SEND-*`。**注釈は 1 つも増えていません**）。

⚠️ **それでも「世界一」とは書きません。** 残っているのは
`unsafe:` の中身・`--no-overflow-check`・`rc[T]` の循環参照、
そして所有権検査の既定が警告であること（⚠️ ただし `spawn` を使うファイルでは
自動でエラーに上がります）です。

✅ **「float の 0 除算だけ揃っていない」という穴は塞ぎました**
（`x / 0.0` も実行時エラー。費用は float 除算が主のループで +9.8%）。

（2026-09-02 のレビューで挙げた「整数があふれても黙る」は
[優先度 A-5](#優先度-a-5--整数のオーバーフロー実装済み-)で埋めました。）

### 到達していないところ

**言語として素直に書けない場面が、はっきり 3 つあります。**

1. **タプルが無い** — `for a, b in pairs:` が書けません。
   複数の値を返すこと自体は `Pair[A, B]`（ジェネリクス）で書けます。
   （⚠️ 演算子の多重定義と `m[i, j]` は[優先度 A-8](#優先度-a-8--演算子の多重定義と-mi-j実装済み-)で入りました。）
2. ~~**内包表記が無い**~~ ✅ **入りました**（集合 `set` はまだありません）。
3. **文字列の書式指定が無い** — `strings.lpad` / `rpad` で桁を揃えます
   （`f"{x:>8}"` は書けません）。

**言語としての大きな穴は埋まりました。** 残りはすべて「書きやすさ」で、
どれにも代替手段があります。

> **クロージャは保留にしました。** 「状態を持った関数」はインタフェースで
> 書けることを確認したためです（[設計](design/future-features.md#3-関数型--実装済み030クロージャ--未実装)）。
> クロージャが足すのは書き味だけで、表現できることは増えません。

## 1.5 いまどのくらいの言語か（Python / Rust / Ada との比較）

**現時点の棚卸しです。** 「実践で使えるか」を判断できるように、
できることではなく**できないこと**を先に書きます。

### 総評

| | 本言語 |
|---|---|
| **書き味** | Python に近い（インデント構文・内包表記・f-string・演算子多重定義） |
| **安全性** | 所有権・借用・可変性の検査、桁あふれと 0 除算の実行時検査、`T \| None`、データ競合の検査。**Rust の考え方を採り、注釈の量は Python 寄り**（ライフタイム注釈は無い） |
| **到達している用途** | **短命なプログラム** — コンパイラ・CLI・バッチ計算・ベアメタル（RISC-V で動作） |
| **到達していない用途** | **長命なプログラム** — サーバ・常駐プロセス（既定で**メモリを解放しません**。§1.5.1） |

### 機能ごとの比較

⚠️ ◎＝ある / ○＝形は違うがある / △＝代替手段でしのげる / ✗＝無い

| | Python | Rust | Ada | **本言語** | 備考 |
|---|---|---|---|---|---|
| 静的型付け | ✗（注釈は任意） | ◎ | ◎ | ◎ | 型注釈は**必須**、推論は無い |
| ジェネリクス | ○（動的） | ◎（トレイト境界） | ◎（generic package） | ○ | 単相化。**境界は書けません**（使えるかは実体化時に分かる） |
| 型引数の推論 | — | ◎ | ○ | ○ | `Box[T]` のような入れ子も見ます。**戻り型にしか出ない型引数は不可** |
| インタフェース / トレイト | ○（duck typing） | ◎ | ○（tagged type） | ○ | `interface`。**デフォルト実装と関連型は無し** |
| 代数的データ型・`match` | ✗ | ◎ | ○（variant record） | ✗ | **enum も無い**（グローバル定数で代用） |

| 整数オーバーフロー | 多倍長 | ○（debug のみ既定） | ◎（`Constraint_Error`） | ◎ | **既定で検査**。`--no-overflow-check` で外せる |
| 範囲型・部分型 | ✗ | ✗ | ◎（`range 1 .. 100`） | ✗ | Ada がいちばん強い領域 |
| 契約（事前条件・不変条件） | ✗ | ✗ | ◎（Pre/Post/Invariant） | △ | `assert` のみ |
| 形式検証 | ✗ | ○（外部ツール） | ◎（SPARK） | ✗ | |
| モジュールの名前空間 | ◎ | ◎ | ◎ | ✗ | **1 ファイル = 1 名前**で、名前はプログラム全体で一意（§1.5.2） |
| パッケージ管理 | ◎ pip | ◎ cargo | ○ Alire | ○ | **`{{pm}}`**。レジストリ無し・git 直指し・MVS |
| 標準ライブラリの広さ | ◎ | ○ | ○ | △ | 数値計算・作図・表・JSON・集合・ファイルシステムはある。**ネットワーク・正規表現・日付が無い** |
| ベアメタル | ✗ | ◎ | ◎ | ◎ | RISC-V で動作。`unsafe:`・生ポインタ・インライン `asm` |

### 1.5.1 いちばん大きな穴 — 既定で解放しない

**これが「実践で使えるか」を分ける最大の一点です。**

言語仕様 §9 のとおり、v1 は `malloc` するだけで `free` しません。
`--drop` を付けるとスコープの出口に解放が入りますが、**既定ではありません**。
本命が「短命なコンパイラ」だったので、プロセス終了に任せる判断でした。

**距離を測り直しました**（`PLC_EXTRA_FLAGS=--drop tests/run_tests.sh`）:

| | 件数 |
|---|---|
| 全ケースに `--drop` を付けて実行 | 531 件中 **10 件が失敗** |
| ①「壊れて当然」（**診断が出ている**。借用や共有の警告を出すためのケース） | 5 件 |
| ② **v1 の参照セマンティクス前提で書かれたケース**（`E-MOVE-1` が出ている） | 5 件 |
| ③ **診断が出ないまま壊れるケース** | **0 件** ✅ |

**★ ③がゼロになりました。** `--drop` で壊れるケースは、いま全部
**コンパイル時に何か言っています**。残っているのは「言っているのに直していない」
ぶんだけで、黙って落ちるものはありません。

⚠️ **内訳は当初の見立てと違いました。**
「`ownck` が別名を追い切れていない」と書いていましたが、②の 5 件
（`class_ref_eq` / `class_reference_semantics` / `list_reference_semantics` /
`nullable_linked_list` / `lexer_perf_note`）は**処理系の不具合ではありません**。
どれも `b = a` や `a.next = b` を「両方の名前が生き続ける」前提で書いており、
v2 の移動規則（§3.1）に照らすと**使用後移動そのもの**です。実際、`ownck` は
どのケースにも `E-MOVE-1` を出しています。`--drop` を付けると codegen が
移動元を `null` にするので、そこで初めて挙動に出る、という順序でした。

**本当の穴は 1 件でした。** `tests/mods/mod_class_across` は
**診断が 1 つも出ないまま** segfault していました（実測 exit=139）。

```python
xs: list[ast.Node] = [ast.make(2), ast.make(3)]
a: ast.Node = ast.Node(0)
a.next = xs[1]        # ← 借りものを、所有しているフィールドへ入れた
```

その借りものを**所有スロット**（フィールドやリストの要素）へ入れると

`E-BORROW-3` はこの形を見ていませんでした（借用**引数**しか追っていない）。

#### 🐛 A-21c — 借りものを `own` 引数へ渡す形が検査されていない

`src/ownck.c :: move_expr` は、添字・フィールド・グローバルから読んだ
**借りもの**を所有スロットへ入れた場合に `E-BORROW-7` を出しますが、
その判定が `MV_FIELD` と `MV_APPEND` **だけ**でした。
`MV_OWN_ARG`（`own` 引数へ渡す）が漏れています。

```python
class Box:
    s: str
    def init(self, s: own str) -> None:
        self.s = s

xs: list[str] = ["hello" + "!"]
b: Box = Box(xs[0])      # ← 借りものを own 引数へ。★ 診断が 1 つも出ない
```

`--drop` を付けると `b` と `xs` の両方が同じ実体を解放します。
AddressSanitizer は `heap-use-after-free`（`core.c :: pl_drop_str`）と言います。

**✅ A-21c は塞ぎました。** `MV_OWN_ARG` を判定に足し、
`tests/cases/warn_store_borrow_own_arg{{ext}}` で固定しました。
⚠️ ただし **`selfhost/` にこの形は 1 件もありませんでした**（507 ケースでも 0 件）。
**クラッシュの原因は別**です。次の A-21d がそれです。

#### 🐛 A-21d — `return self.<フィールド>` が、呼び出し側では所有になる

**これが `--drop` を既定にできない本当の理由です。** 仕様 §4.5 は
「`self` のフィールドの借用を返すこと」を許しています。ところが
**戻り値の型に「これは借用だ」と書く手段がありません**。
そのため呼び出し側は所有として受け取り、自分でも解放します。

```python
class Maker:
    out: list[int]
    def init(self) -> None:
        self.out = []
    def run(mut self) -> list[int]:
        self.out.append(1)
        return self.out          # §4.5 が許す「self のフィールドの借用を返す」

def make() -> list[int]:
    m: Maker = Maker()
    return m.run()               # ★ m はここで drop → self.out も解放される

def main() -> int:
    xs: list[int] = make()       # ★ xs も所有として解放する → 二重解放
    print(str(len(xs)))
    return 0
```

**`lexer.tokenize` がそのままこの形でした。** だから `--drop` 版の
コンパイラは、字句解析を 1 回通すだけで落ちていました。
AddressSanitizer は `heap-use-after-free`（`core.c :: pl_drop_list`）と言います。

⚠️ **これは検査の漏れではなく、言語の表現力の問題です。**
借用検査は「借りは呼び出しより長生きしない」を守れますが、
**戻り値が借りかどうかを型に書けない**以上、呼ぶ側は所有と見なすしかありません。

**選べる道（どれも §0 ①「書きやすさが下がるなら入れない」に照らして選ぶこと）**

| 道 | 中身 | 代償 |
|---|---|---|
| (a) `return self.f` を所有型について禁じる | `copy(self.f)` か「self から取り出す」を書かせる | 既存コードの書き換え。`lexer.run` などが該当 |
| (b) **self から取り出す**（`std::mem::take` 相当） | `return take(self.f)` を入れ、`self.f` は空になる | 新しい組み込み関数 1 つ。**書き味はほぼ変わらない** |
| (c) 戻り値に借用の印を付ける | `-> borrow list[int]` のような記法 | **注釈が増える**。§0 ① に反する |
| (d) 返すときに複製する | 暗黙に `copy` | 黙って遅くなる。§0 に反する |

**★ (b) が本命に見えます。** `self.out` を返して `self` を空にするのは
「作って返す」という実際の使われ方（`Lexer.run` / `Parser.program`）と一致し、
注釈は 1 つも増えません。

#### ✅ A-21d は `move_out` で塞ぎました

**`move_out(場所)`** を足しました。所有権を取り出し、その場所には
**空の値**（`str` なら `""`、`list[T]` なら空リスト）を書き戻します。

```python
def run(mut self) -> list[rc[token.Token]]:
    return move_out(self.out)     # self.out は空のリストになる
```

- 対象は `str` と `list[T]`、場所はフィールド・添字・グローバル
- **retain も release も出しません**（参照数は動かず、持ち主が移るだけ）
- C 版とセルフホスト版の両方に入れ、**IR がバイト単位で一致**することを確認

⚠️ **名前は `take` から `move_out` に変えました。** `take` はリポジトリ内で
29 箇所（`lib/frame{{ext}}` の `Frame.take` を含む）に使われていて、
組み込みにすると**利用者のコードが壊れます**。**組み込みを足すときは、
先に既存の識別子と衝突しないか数えること**（§0 ① の実例）。

同じ形の不具合を 3 件直しました（どれも AddressSanitizer で実証）。

| 箇所 | 症状 | 直し方 |
|---|---|---|
| `lexer.run` | `return self.out` で二重解放 | `move_out`（Lexer は手放す） |
| `module.path_for` | `return hits[0]` で解放済みを返す | `move_out`（リストは捨てる） |
| `codegen.intern_str` | `return s.label` で解放済みを読む | **`copy`**（StrLit は持ち続ける） |

検査も足しました。**`E-BORROW-8`** — 自分が所有しているものの一部を返すと
警告します（`--deny-store-borrow` でエラー）。

#### 📏 いま `--drop` でどこまで解放されるか（実測）

1,000,000 回まわして最大 RSS を測りました。

| ループの中身 | 既定 | `--drop` | |
|---|---|---|---|
| `xs: list[int] = []; xs.append(i)` | 61.8 MB | **0.6 MB** | ✅ 頭打ち |
| `s: str = str(i)` | — | **0.6 MB** | ✅ 頭打ち |
| `s: str = "x" + "y"` | — | **0.6 MB** | ✅ 頭打ち |
| `s: str = "x" + str(i)` | 31.4 MB | **16.0 MB** | ❌ 増え続ける |

**リストとオブジェクトは正しく解放されるようになりました。**

#### ✅ A-21e — 入れ子の式の「中間の一時値」を解放するようにしました

`"x" + str(i)` の **`str(i)` の結果**は、どこにも束縛されないまま
`pl_str_concat` に渡され、誰も解放していませんでした。

`is_owned_temp()`（新しく作られて、ほかに持ち主がいない値か）を足し、
**所有権が移らない消費箇所だけ**で解放します。

| 解放する場所 | 例 |
|---|---|
| 二項演算のオペランド | `"x" + str(i)` / `a == str(i)` |
| 組み込みの引数 | `len(str(i))` / `print("x" + s)` |
| **借用**の仮引数へ渡した実引数 | `borrow("z" + s)` |

⚠️ **所有権が移る場所では解放しません。** `xs.append(str(i))` は
リストが受け取るので、解放すると二重解放です。

**📏 実測（100 万回まわして最大 RSS）**

| ループの中身 | 前 | 後 |
|---|---|---|
| `s: str = "x" + str(i)` | 16.0 MB | **0.6 MB** |
| `len(str(i))` | 16.0 MB | **0.7 MB** |
| `len("a" + str(i))` | 16.0 MB | **0.7 MB** |
| `borrow(str(i))`（関数・借用引数） | 16.0 MB | **0.6 MB** |
| `xs.append(str(i))` | 0.7 MB | **0.7 MB** |
| `b.see("x" + str(i))`（**メソッド**引数） | 16.0 MB | 16.0 MB ❌ |

**⚠️ 旗の向きで二重解放を入れかけました。** 最初は
`passed_by_own`（既定 `false` ＝ 解放する）にしていて、`check_call_sig` を
通らない**メソッド呼び出し**の `own` 引数まで解放し、`drop_fields` と
`drop_lib_dict` が `heap-use-after-free` で落ちました。
`arg_is_borrowed`（既定 `false` ＝ **解放しない**）に反転して直しています。

> ★ **旗は「既定が安全側」になる向きに作ること。** 分からない経路では
> 漏れるだけで済み、壊れません。メソッド引数がまだ漏れるのは、この
> 安全側の既定によるものです（仮引数のモードを codegen に渡していない）。

⚠️ 入れ子の呼び出し `f(g(x))` では、`g` の呼び出しが `f` の引数一時値まで
解放しないよう、引数ごとに控えを待避します。解放は **`emit_call` の後**です
（引数を作った直後に解放すると、まだ渡していない値を消します）。

固定: `tests/cases/drop_temps{{ext}}`（5 つの形を 1 本に。`tests/drop_asan.sh`
が `--drop` + AddressSanitizer で回すので、**解放しすぎも**ここで捕まります）。

#### 🐛 残り — メソッドの実引数

`check_call_sig` は**通常の関数専用**で、メソッドは別経路です。仮引数の
モードが codegen に届かないので、安全側に倒して解放していません。
埋めるには、メソッドの検査経路でも `arg_is_borrowed` を立てる必要があります。

> **残っていること（A-21）**: 順序は
> **①`selfhost/` の 40 件（✅ 済）→ ②`MV_OWN_ARG` の検査（✅ 済）→
> ③`move_out` と A-21d（✅ 済）→ ④A-21e：中間の一時値（✅ 済。メソッド引数だけ残）→
> ⑤`--drop` 版で 3 段ビルドを通す → ⑥v1 前提のテストを v2 の書き方へ移す →
> ⑦`--drop` を既定にする → ⑧`--no-drop` を逃げ道に残す**。
> **これが終わるまで、サーバや常駐プロセスは書けません。**

### 優先度 A-1 — 使ってみて出た不足（実装済み ✅）

| **複数戻り値** ✅ | タプル型 `(A, B)` と分解代入 | 分解代入では**型注釈を書かせない**（下の ③）。1 要素のタプルは入れない |

### 優先度 A-2 — `//` と `%` の符号（実装済み ✅）

**`-7 // 2` が Python では `-4`、本言語では `-3` でした。** C の `sdiv` を
そのまま使っていたためです。[§0 の①](#0-この言語が譲らないこと)（書きやすさが
下がるなら入れない）に照らすと、これは**書きやすさの穴**でした。

**Python と同じ切り下げ（floored）にしました。**

| 式 | 前 | 後（＝ Python） |
|---|---|---|
| `-7 // 2` | `-3` | **`-4`** |
| `7 // -2` | `-3` | **`-4`** |
| `-7 % 2` | `-1` | **`1`** |
| `7 % -2` | `1` | **`-1`** |

**商と余りは一組です。** 片方だけ直すと恒等式 `a == (a // b) * b + (a % b)` が
崩れるので、両方を同時に直しました。

#### ⚠️ 速さは落ちていません

`//` と `%` は **0 除算の検査のためどのみち `pl_floordiv` / `pl_mod` を通ります**
（規約 R10）。増えたのは関数の**中**の比較 2 つだけで、**呼び出しの回数は
前と同じ**です。A-3 で消したのは「呼び出し」であって、この検査ではありません。

#### 直した場所は 1 か所だけです

両実装の codegen はどちらも `call @pl_floordiv` を出すだけなので、
**変更は `runtime/core.c` の 2 関数に収まりました。** IR は 1 バイトも変わらず、
[§4 の 5](#4-設計上ぶれさせないこと)（2 実装の一致）は自動的に保たれています。

#### ついでに埋めた穴

`-9223372036854775808 // -1` は C では**未定義動作**で、黙って SIGFPE で
落ちていました。名前を付けて落とすようにしています（`%` のほうは `0` を返します）。

**検証:** Python と総当たりで突き合わせました（15 × 15 の組で `//` `%` 450 通り、
全一致）。番人テストは `tests/cases/floordiv_sign{{ext}}` です。

### 優先度 A（旧）— 埋まったもの

**言語の表現力の穴は埋まりました。** 残っていたタプルも、
`pair.Pair[A, B]`（標準ライブラリ）で複数戻り値が書けることを確認したため
下げました。タプルが足すのは分解代入（`a, b = f()`）の構文だけです。

### 優先度 A-3 — 添字とフィールド参照を IR に（実装済み ✅）

**`xs[i]` が非インライン化のランタイム関数呼び出しでした。** codegen は
`pl_list_get_i64` / `pl_list_get_ptr` の `call` を出し、ランタイムは
`build/runtime.a` として別にリンクされます。LTO を使っていないので
`-O2` でもインライン化されません。**同じことが `pl_check_not_none`
（フィールド参照のたびに 1 回）にも起きていました。**

**3 つとも入りました**（C 実装・本言語実装の両方）。

| 直したもの | 内容 |
|---|---|
| **① 添字を IR に展開する** ✅ | `getelementptr` ＋ 境界検査を codegen が直接出す（`gen_index_addr`） |
| **② None 検査を IR に展開する** ✅ | フィールド参照の `pl_check_not_none` 呼び出しを無くす（`gen_not_none`） |
| **③ `panic` / `exit` に `noreturn`** ✅ | 付けないと LLVM が「戻るかも」と見て、**ループ内の load を外に出せない** |

実測（macOS x86_64、C は clang -O2、プロセス起動 4ms を差し引き）:

| 種目 | C | 本言語（前） | 本言語（後） | 倍率（前 → 後） |
|---|---|---|---|---|
| 整数ループ 2000万回 | 63 ms | 156 ms | 132 ms | 2.5 → **2.1 倍** |
| float 級数 2000万項 | 19 ms | 111 ms | 104 ms | 5.8 → **5.5 倍** |
| **行列積 256³** | 7 ms | **485 ms** | **36 ms** | **61 → 5.1 倍**（⚠️ B1） |
| 行列積（`linalg.Matrix`） | 5 ms | 528 ms | **134 ms** | — |
| 自己コンパイル（型検査まで） | 50 ms | 90 ms | **70 ms** | 1.8 → **1.4 倍** |

⚠️ **この表の「C の 5.1 倍」は、あとで誤りと分かりました。**
プロセス起動 4 ms を C の総時間（9 ms）から引いたことで分母が半分になり、
比が小さく出ています。起動が無視できる条件で測り直すと **8 倍**です。
[§3-B1](#b1--c-の-51-倍は起動時間の引き算が効きすぎた数字です) を見てください。

**行列積が 13 倍速くなりました。** 内側ループの
`c[i][j] = c[i][j] + aik * b[k][j]` が関数呼び出し 5 回だったのが、
`getelementptr` と `load` / `store` になったためです。

#### ⚠️ 境界検査は外していません

遅かったのは検査ではなく**呼び出し**でした。検査は IR に出しています。

```llvm
  %len = load i64, ptr %lenp
  %ni  = select i1 %isneg, i64 %plus, i64 %i   ; 負の添字は末尾から
  %inb = icmp ult i64 %ni, %len                ; ★ 符号なし比較 1 回で両側を見る
  br i1 %inb, label %idx.ok.0, label %idx.bad.0
idx.bad.0:
  call void @pl_index_fail(i64 %ni, i64 %len)
  unreachable
```

`icmp ult` ひとつで `i < 0` と `i >= len` の両方を捕まえます
（`len >= 0` なので、負の `i` は符号なしでは巨大な値になります）。
**IR に出したことで、LLVM が検査をループの外へ持ち上げたり、
範囲が自明なときに消したりできるようになりました。**
[§0 の ②](#0-この言語が譲らないこと)に従い、`unsafe` な添字は入れません。

#### `-flto` は要りませんでした

案②として挙げていた `-flto` を試しましたが、**効果はほぼゼロ**でした
（`linalg` 版で 319 ms → 313 ms）。呼び出しを消すのは
リンカではなく codegen の仕事だった、ということです。

#### まだ残っていたもの → A-4 で解決

`linalg.Matrix`（平坦な `list[float]`）が二重リストより 3.7 倍遅い件は
**A-4 で直りました**（下）。原因は別名解析ではありませんでした。

計測コードは `bench/`（git 管理外）にあります。

> **⚠️ Rust との比較は未実施です。** 開発機の `rustc` が 1.50（2021 年）で、
> 現在の macOS リンカと組めませんでした。Rust も `Vec` の添字で境界検査を
> するので、**条件としては C より本言語に近い**比較対象です。

### 優先度 A-4 — panic の経路がインライン化を止めていた（実装済み ✅）

**`linalg.Matrix` の行列積が 143 ms で、二重リストの 42 ms より 3.4 倍
遅いままでした。** A-3 の時点では原因を「別名解析が足りない」と見立てて
いましたが、**測ったら違いました。**

#### ⚠️ 別名解析（TBAA）は「このときは」効きませんでした

まず仮説どおり TBAA を試しました。クラスのフィールド／list のヘッダ／
list の要素に別々の型タグを付け、互いに別名ではないと LLVM に伝えます。

**結果は 142 ms → 146 ms。ゼロでした。**

> **⚠️ この結論は後で覆りました。** インライン化の詰まりに隠れていただけで、
> 下の ① を入れてから測り直すと **効きます**（60 → 48 ms）。
> [敵対的レビュー](#3-敵対的レビュー2026-09-02)の A1 を見てください。
> **「効かなかった」は「そのときのボトルネックでは効かなかった」でしかない、
> という教訓です。**

最適化後の IR を読んで、本当の原因が分かりました。

```llvm
  tail call void @linalg.Matrix.check(ptr %c, i64 %i, i64 %j)   ; ★ 消えていない
  tail call void @linalg.Matrix.check(ptr %c, i64 %i, i64 %j)
  tail call void @linalg.Matrix.check(ptr %b, i64 %k, i64 %j)
```

**`Matrix.check` が内側ループで 1 周に 3 回、呼び出しのまま残っていました。**
`-mllvm -inline-threshold=10000` を付けると 142 ms → 57 ms になります。
つまり**インライン化の問題**で、メモリの別名の問題ではありませんでした。

#### なぜインライン化されないのか

`check` の中身は比較 4 つですが、**失敗したときのメッセージ**が大きいのです。

```python
def check(self, i: int, j: int) -> None:
    if i < 0 or i >= self.rows or j < 0 or j >= self.cols:
        panic("linalg.Matrix: 添字が範囲外です（" + str(i) + ", " + str(j) + "）")
```

連結 4 回 ＋ `str()` 2 回で**呼び出し 6 回ぶん**の費用が `check` の大きさとして
数えられます。LLVM の既定のしきい値を超えるので、`check` は丸ごと
インライン化を諦められます。**まず通らない経路が、通る経路の速さを決めていました。**

#### 直した 2 つ

| | 直したもの | 効果（単独） |
|---|---|---|
| ① | **`panic` / `exit` / `pl_index_fail` / `pl_none_fail` の宣言に `cold` を付ける**（コンパイラ側。C 実装・本言語実装の両方） | 143 → 100 ms |
| ② | **メッセージの組み立てを別関数に切り出す**（`lib/linalg{{ext}}` の `Matrix.index_fail`） | 効果なし（単独では） |
| | **①＋②** | **143 → 62 ms** |

**⚠️ 片方だけでは足りません。** ② だけだと `check` は小さくなりますが、
切り出した先の呼び出しが今度は費用として数えられます。① を入れると
その呼び出しが「まず通らない」ものとして割り引かれ、両方そろって効きます。

`noreturn` は「戻らない」ことしか言いません。**インライン化の見積りに効くのは
`cold` のほうです。** A-3 で `noreturn` を付けたときに気づけなかった点です。

#### ⚠️ ② はループの中の検査にだけ効きます

同じ形の `linalg.same_len`（`add` / `sub` / `mul` が呼ぶ長さの検査）にも
切り出しを試しましたが、**少し遅くなったので戻しました**（0.31 → 0.34 秒）。
`same_len` は**ループの外**で 1 回呼ばれるだけで、インライン化されても
内側ループは変わらないためです。

**切り出す価値があるのは「ループの中から呼ばれる検査」だけ**、というのが
測って分かったことです。①（`cold`）のほうは利用者のコード全体に効くので、
コンパイラ側に入れてあります。

#### 実測

| 種目 | C | 本言語（前） | 本言語（後） |
|---|---|---|---|
| **行列積（`linalg.Matrix`）** | 8 ms | **143 ms** | **62 ms** |
| 行列積（二重リスト） | — | 41 ms | 41 ms |
| 整数ループ 2000万回 | 69 ms | 155 ms | 156 ms |
| float 級数 2000万項 | 23 ms | 108 ms | 111 ms |
| 自己コンパイル（型検査まで） | 54 ms | 58 ms | 59 ms |

（プロセス起動 4 ms を含んだ値です。`linalg` 以外は誤差の範囲で変わりません。）

**二重リストとの差は 3.4 倍 → 1.5 倍になりました。**

#### 残っているもの

C の平坦配列（8 ms）にはまだ差があります。二重リスト版（41 ms）との
1.5 倍の差も残っています。**続きは[敵対的レビュー](#3-敵対的レビュー2026-09-02)で
測り直しました** — TBAA はここから先で効きます。

### 優先度 A-5 — 整数のオーバーフロー（実装済み ✅）

**`9223372036854775807 + 1` が黙って `-9223372036854775808` になっていました。**
0.6.0 から**あふれたら実行時エラー**です。

| 演算 | 前 | 後 |
|---|---|---|
| `+` `-` `*` | 2 の補数で折り返す | **panic**（`llvm.sadd/ssub/smul.with.overflow` を IR に展開） |
| 単項 `-` | `-INT_MIN` が `INT_MIN` | **panic** |
| `**` | `2 ** 64` が `0` | **panic**（`pl_ipow` の中で 1 段ごとに検査） |
| `int(float)` | `int(1.0e30)` が `INT_MIN` | **panic**（C のキャストは未定義動作だった） |
| `int(str)` | `int("99999999999999999999")` が別の数 | **panic** |
| `//` の 0 除算・`INT_MIN // -1` | すでに panic（0.5.1） | 変更なし |

**これで「64bit に収まらない」の扱いが揃いました。** 0.5.1 で作った
「`//` は落ちて `*` は黙る」という非対称が解消しています。

#### 折り返しが目的のところは `wrap_add` / `wrap_sub` / `wrap_mul`

`lib/random{{ext}}` の線形合同法は、折り返しこそが法 2⁶⁴ の計算そのものです。

```python
def next_state() -> int:
    STATE = wrap_add(wrap_mul(STATE, 6364136223846793005),
                     1442695040888963407)
    return STATE
```

⚠️ **`unsafe:` にはしませんでした。** 折り返しはメモリ安全性の問題ではなく
「そういう計算だ」という意図の表明なので、**演算ごとに名前で示します**
（Rust の `wrapping_mul` と同じ考え方）。

#### ⚠️ 速さ — 設計時の「2.4%」は間違いでした

**方式を決めるときに「実測 2.4%」と見積もりましたが、それは整数ループだけの
数字でした。** 全部を測るとこうです。

| 種目 | 検査なし | 検査あり | 比 |
|---|---|---|---|
| 整数ループ 2000万回 | 213 ms | 218 ms | **1.02 倍** |
| 行列積（二重リスト） | 60 ms | 58 ms | **変わらず** |
| **行列積（`linalg.Matrix`）** | **84 ms** | **210 ms** | **⚠️ 2.5 倍** |

（この回は機械が熱で全体に遅く出ています。**比だけを見てください。**
2 回続けて同じ比でした。）

#### なぜ `linalg` だけ 2.5 倍なのか — A-4 と同じ罠です

`Matrix.get` / `set` は `self.data[i * self.cols + j]` を計算します。
この `*` と `+` に検査が付くと**分岐が 2 つ増え**、
[優先度 A-4](#優先度-a-4--panic-の経路がインライン化を止めていた実装済み-)で
やっと収まった `get` / `set` が、**また LLVM のインライン化しきい値を超えます。**

```
matmul の内側ループに残った呼び出し:  Matrix.get × 3、Matrix.set × 1
```

**検査そのものの費用は 13% ほどです**（`-mllvm -inline-threshold=10000` で
測ると 60 → 68 ms）。**残りは全部インライン化が外れたぶんです。**

⚠️ **試して効かなかったもの:**

| 試したこと | 結果 |
|---|---|
| 分岐に `!prof` の頻度情報（`branch_weights` 1:2000）を付ける | **変化なし**。インライン化の見積りは頻度を見ていない |
| `sadd`/`ssub` の intrinsic をやめて算術で判定（`(a^v)&(b^v) < 0`） | 誤差の範囲。単純な intrinsic のままにした |

#### 残っている宿題 → **A-6 で片付けました** ✅

**検査を「インライン化しきい値に優しい形」で出す方法**が要りました。
当時の案は次の 3 つで、**実際に採ったのは（案②を健全にした）4 つめ**です
（[優先度 A-6](#優先度-a-6--桁あふれ検査の費用を下げる実装済み-)）。

| 案 | 内容 |
|---|---|
| 文ごとに 1 分岐 | 式の途中の桁あふれ旗を `or` で束ね、文の終わりで 1 回だけ分岐する。分岐が半分以下になる。⚠️ どの演算であふれたかは言えなくなる |
| 添字計算だけ別扱い | `xs[i * n + j]` は境界検査が後ろに控えている。⚠️ **折り返した添字がたまたま範囲内に入ると別の要素を読む**ので、そのままでは不健全 |
| しきい値を上げる | `clang` に `-mllvm -inline-threshold=...` を渡す。⚠️ 生成物全体が膨らむ（実測：600 にすると効くが、生成物が 13% 大きくなる） |
| **④（採用）添字の中だけ、旗にして範囲検査に相乗り** | 分岐も呼び出しも増えません。⚠️ 折り返した添字は `and` で潰すので**健全**です（案②との違い） |

**逃げ道の `--no-overflow-check` は残してあります**（さらに 1.5 倍速くなります）。

### 優先度 A-6 — 桁あふれ検査の費用を下げる（実装済み ✅）

**0.6.0 の宿題**（「検査をインライン化しきい値に優しい形で出す」）**を片付けました。**
`linalg.Matrix` の行列積が **1083 ms → 530 ms 前後（2.0 倍速く）**なっています。

#### まず、原因を数字で特定しました

A-4 と A-5 では「インライン化のしきい値を超えたらしい」と**推測**していました。
今回は LLVM に直接聞きました。

```console
$ clang -O2 -Rpass-missed=inline ...
remark: 'linalg.Matrix.get' not inlined into 'linalg.matmul'
        because too costly to inline (cost=225, threshold=225)
```

**`cost=225` / `threshold=225` — 1 点足りずに落ちていました。**
`set` は 245 でした。何が 225 を占めているのかを、IR を書き換えて測りました。

| 外れの経路をどう書くか | `get` / `set` はインライン化されるか |
|---|---|
| `call void @pl_overflow_fail(i64 2)`（いまの形） | ❌ されない（cost 225 / 245） |
| 引数を無くす `call void @pl_overflow_fail0()` | ❌ されない（cost 255 / 235） |
| `call void @llvm.trap()`（**組み込み命令**） | ✅ **される** |
| `unreachable` だけ | ✅ される |

**⚠️ 費用は「検査の計算」ではなく「呼び出しがあること」でした。**
LLVM の見積りは、**外れの経路の呼び出し 1 つにつき約 25 点**を数えます。
`cold` を付けても引かれません（`cold` が効くのは「その呼び出しを
インライン化するか」の判断で、「囲む関数の大きさ」ではありません）。

`Matrix.get` には外れの経路が **5 つ**ありました
（`pl_none_fail` ×1・`Matrix.index_fail` ×1・`pl_index_fail` ×1・
桁あふれ ×2）。**225 点のうち約 125 点が、一度も通らない経路の呼び出し**です。

#### 直し方：あふれの報告を、**もとからある範囲検査に相乗りさせる**

`xs[i * cols + j]` の `*` と `+` は、**分岐せず旗（`i1`）を立てるだけ**にします。
最後に「**範囲内 かつ あふれていない**」を 1 回だけ分岐します。

```llvm
  %m   = call {i64, i1} @llvm.smul.with.overflow.i64(i64 %i, i64 %cols)
  %mo  = extractvalue {i64, i1} %m, 1
  %a   = call {i64, i1} @llvm.sadd.with.overflow.i64(i64 %mv, i64 %j)
  %ao  = extractvalue {i64, i1} %a, 1
  %ovf = or i1 %mo, %ao                  ; ★ 旗をまとめる（分岐しない）
  %inb = icmp ult i64 %idx, %len
  %nov = xor i1 %ovf, true
  %ok  = and i1 %inb, %nov               ; ★ 範囲内 かつ あふれていない
  br i1 %ok, label %idx.ok.4, label %idx.bad.4
idx.bad.4:
  call void @pl_index_fail(i64 %idx, i64 %len, i64 %z)   ; ★ もとからある 1 つだけ
  unreachable
```

**外れの経路の呼び出しは増えません。分岐も増えません。**
足したのは `or` / `xor` / `and` / `zext` の 4 命令だけです。

| | 前（0.6.0） | 後（0.6.1） |
|---|---|---|
| `Matrix.get` の cost | **225**（threshold 225） | **175** ✅ |
| 内側ループの呼び出し | `get` ×3・`set` ×1 | **なし**（全部インライン化） |

#### ⚠️ 健全性 — 「検査を省く」案とはここが違います

[レビュー E の案②](#残っている宿題--a-6-で片付けました-)は「添字計算の検査は後ろの範囲検査に任せる」
というものでしたが、**折り返した添字がたまたま範囲内に入る**ので不健全でした。

```python
xs: list[int] = [1, 2, 3, 4]
print(str(xs[4611686018427387904 * 2]))   # 2^63 → 折り返すと 0（＝範囲内！）
```

**検査を省いていないので、この例は正しく落ちます**（`and` で潰しているため）。
番人は `tests/cases/rt_overflow_index{{ext}}` です。

#### ⚠️ 意味の違いが 1 つだけあります

| | 前 | 後 |
|---|---|---|
| 止まる場所 | あふれた演算のところ | **添字の計算が終わったところ** |
| 診断 | `integer overflow in *` | `integer overflow in index computation` |

`xs[a * b + f()]` は、`a * b` があふれても **`f()` が呼ばれてから**落ちます。
どの演算子であふれたかも言いません（旗を 1 つにまとめているため）。
**添字の外の算術は今までどおり**、演算ごとにその場で落ちます。

#### 実測（512³、`-O2`、プロセス内で計測）

| 種目 | 0.6.0 | **0.6.1** | 検査なし（`--no-overflow-check`） |
|---|---|---|---|
| **行列積 `linalg.Matrix`** | 1083 ms | **530 ms** | 350 ms |
| 行列積 二重リスト | 256 ms | 256 ms | 253 ms |
| 整数ループ 2000万回 | 160 ms | 160 ms | 155 ms |

**⚠️ まだ検査なしより 1.5 倍遅いままです。** 残りは
「あふれの検出そのもの（`with.overflow` ＋ `or`）」と、
そこから先の[ベクトル化が開かない](#b5-c-だけがベクトル化されています)ぶんです。
最適化後のアセンブリを読むと、内側ループで `self.cols` の**読み直しが
消えていません**（`c` への書き込みと別名かもしれない、と見えるため）。
**次は [TBAA](#a1--tbaa-は効かないは誤りでした)です。**

### 優先度 A-7 — 別名解析（TBAA）（実装済み ✅）

**レビュー A1 で「効く」と分かっていたものを、codegen に入れました。**

LLVM は既定で「ポインタはどれも同じ場所を指すかもしれない」と考えます。
だから `c.data[i] = v` と書いた直後の `self.cols` の読み出しは
「書き換わったかもしれない」と見なされ、ループの外に出せません。

**重ならない 3 種類に名前を付けて、別物だと言い切ります。**

```llvm
!0 = !{!"<言語名>"}              ; 根（langinfo が決める）
!1 = !{!"field",    !0}            ; クラスのフィールド
!2 = !{!"listhdr",  !0}            ; list のヘッダ（data ポインタと len）
!3 = !{!"listelem", !0}            ; list の要素
```

**健全性**：`pl_list_new` はヘッダと要素配列を**別々に確保**し
（`runtime/core.c`）、クラスのオブジェクトもまた別の確保です。
この 3 つは決して重なりません。**タグを付けないアクセスは
「何とでも別名かもしれない」**と扱われるので、ローカル変数・グローバル・
文字列・`unsafe:` の生ポインタ・`extern` には付けません（安全側）。

#### 実測 — **同じ IR から `!tbaa` だけを削って A/B**

```bash
sed 's/, !tbaa ![0-9]*//' prog.ll > no_tbaa.ll   # 違いはこれだけ
```

| 種目（512³、`-O2`） | TBAA なし | **TBAA あり** | |
|---|---|---|---|
| 行列積 二重リスト | 269 ms | **226 ms** | **−16%** |
| 行列積 `linalg.Matrix` | 528 ms | **488 ms** | **−8%** |
| 整数ループ 2000万回 | 159 ms | 159 ms | 変わらず（当然） |

#### ⚠️ 試作のときの見積り（−20%）より小さく出ました

レビュー A1 では `linalg` が 60 → 48 ms（−20%）でした。今回は −8% です。
**試作は A-6 の前、つまりインライン化が外れていた状態での測定**です。
ボトルネックを 1 つ外すと、次の効き方は変わります。
（二重リストのほうは −16% で、試作の予想どおりでした。）

#### 残っているもの

最適化後の IR を読むと、内側ループに**フィールドの読み直しがまだ残ります**。
TBAA が「別名ではない」と言っているので、**理由はもう別名解析ではありません**
（ループ最適化と、インライン化されるまでの実行順の問題と見ています）。

**ベクトル化は開きませんでした。**

| | SIMD 命令 |
|---|---|
| C 平坦配列 | 20 |
| 本言語 `linalg`（TBAA あり／なし） | 6 / 6 |
| 本言語二重リスト | 0 |

TBAA は**別名を外すだけで、検査の分岐は減らしません**。
[B5](#b5-c-だけがベクトル化されています) のとおり、次は
**境界検査をループの外へ出す**ことです。

### 優先度 A-8 — 演算子の多重定義と `m[i, j]`（実装済み ✅）

**レビュー D1 の「行列の式が読めない」を直しました。**

```python
c = a * b + d          # 前は madd(matmul(a, b), d)
print(str(m[i, j]))    # 前は m.get(i, j)
m[i, j] += 1.0         # 前は m.set(i, j, m.get(i, j) + 1.0)
```

#### 入れ方 — **意味解析で読み替えるだけ**

`a + b` の左辺がクラスで、そのクラスに `__add__` があれば
**`a.__add__(b)` に読み替えます。** それだけです。

| パス | 変えたか |
|---|---|
| 字句解析 | 変えていません |
| 構文解析 | `m[i, j]` の**カンマ**だけ（添字を並びにしました） |
| **意味解析** | **ここだけ**（`ND_BINOP` → `ND_METHOD` の読み替え） |
| codegen / IR | **1 行も変えていません** |

ふつうのメソッド呼び出しになるので、所有権検査も `--drop` も
既存のまま通ります。**2 実装の IR 一致も自動的に保たれました。**

#### 対応する演算子

| 演算子 | メソッド | | 演算子 | メソッド |
|---|---|---|---|---|
| `+` `-` `*` | `__add__` `__sub__` `__mul__` | | `==` | `__eq__` |
| `/` `//` `%` `**` | `__truediv__` `__floordiv__` `__mod__` `__pow__` | | `!=` | `__ne__`（無ければ `not __eq__`） |
| 単項 `-` | `__neg__` | | `<` `<=` `>` `>=` | `__lt__` `__le__` `__gt__` `__ge__` |
| `m[i]` / `m[i, j]` | `__getitem__` | | `m[i] = v` | `__setitem__` |

#### 決めたこと

| | 決めたこと | なぜ |
|---|---|---|
| 名前 | **Python と同じ `__add__`** | ふつうのメソッドと必ず区別できる必要があります。`add` にすると `linalg.Matrix.add` のような既存のメソッドが、書いた覚えのないところで演算子として呼ばれます |
| 反転 | **入れません**（`__radd__` は無い） | `2.0 * m` は書けません（`m * 2.0` と書きます）。**左辺の型だけ**で決まるほうが、どのメソッドが呼ばれるか読んで分かります |
| `!=` | `__eq__` から**導けます** | Python と同じ。`__eq__` だけ書けば両方使えます。⚠️ `__eq__` が `bool` を返さないときはエラーにします |
| 添字の数 | **いくつでも**（`m[i, j, k]` も可） | `__getitem__` の引数の数と合っていればよい、という規則ひとつで済みます |
| `list` / `str` | **1 つだけ** | `xs[0, 1]` は「2 次元の添字が使えるのは `__getitem__` を定義したクラスだけ」と言って落とします |

#### `linalg.Matrix` に入れました

⚠️ **`*` は行列の積です（numpy とは違います）。** numpy の `a * b` は
要素ごとの積、`a @ b` が行列の積ですが、本言語に `@` はありません。
数学の書き方に合わせました。**要素ごとの積は `mmul(a, b)`** のままです。

⚠️ **スカラー倍（`a * 2.0`）は書けません。** 多重定義は左辺の型だけで
決まり、引数の型では選び分けないためです（`mscale(a, k)` を使います）。

### 優先度 A-10 — `in` の多重定義とカンマ代入（実装済み ✅）

**レビュー D2「Python から来ると必ず引っかかるもの」を 2 つ埋めました。**

```python
if "a" in d:         # dict の in（前は d.has("a")）
    ...
a, b = b, a          # 入れ替え（前は書けなかった）
```

#### `in` は `__contains__`

A-8 の仕組みをそのまま使います。**ただし `in` だけは右辺（入れ物）の型で
決まります** — Python の `__contains__` と同じで、「入れ物に聞く」演算子だからです。
`not in` は結果を反転させます。`lib/dict{{ext}}` に 1 メソッド足しただけで
`k in d` が書けるようになりました。

#### `a, b = b, a`

**構文解析での脱糖です**（`for` や複合代入と同じ手）。

```
a, b = b, a   →   swap.0 = b       ← 右辺を先に全部読む
                  swap.1 = a
                  a = swap.0
                  b = swap.1
```

**右辺を全部読んでから書く**ので、入れ替えが正しく動きます。
左右の数が違えばコンパイルエラーです。

> **⚠️ こちらは「代入」で、宣言は兼ねません。** 宣言も兼ねるのは
> `q, r = f()`（右辺が**タプル 1 つ**）のほうです。区別の理由は、
> 入れ替えが「**既にある 2 つ**を入れ替える」操作だからです。

#### ⚠️ 隠し変数を「借り」にしたら二重解放で壊れました

脱糖が作る隠し変数は、これまで**必ず借りもの**として扱っていました
（`for.it.N` は「対象を 1 回だけ評価するための借り」なので、それで正しい）。
`swap.N` を同じ扱いにしたところ、`--drop` を付けると壊れました。

```
swap.0 = b        ← b は「自分のもの」と思ったまま
a = swap.0        ← a の古い値を解放する。だが swap.1 がそれを指している
b = swap.1        ← 解放済みの領域を b に入れてしまう   → out of memory
```

**`swap.N` だけは所有にしました**（`src/ownck.c` の `is_owning_hidden`）。
右辺を読んだ時点で元の変数が null 化されるので、解放は 1 回だけになります。
番人は `tests/cases/drop_swap{{ext}}`（ASan 付きで走ります）。

**教訓：脱糖で変数を作るときは「借りか、所有か」を必ず決めること。**
既定（借り）のまま足すと、`--drop` を付けたときだけ壊れます。

#### 残っている D2 の項目

| 機能 | 状態 |
|---|---|
| ~~内包表記~~ ✅ | **入れました**（`ND_LISTCOMP` 節点。⚠️ 所有権検査も忘れずに） |
| `t[0]`（タプルの添字） | 未実装 |
| f-string の書式 `f"{x:>8}"` | 未実装（`strings.lpad` / `rpad` があります） |
| 既定引数・キーワード引数・`set`・`lambda`・入れ子の関数・`while-else` | 未実装 |

⚠️ **内包表記は「構文解析での脱糖」では入れられません。** `for` や
カンマ代入と違い、**式の位置**に現れるためです。文に持ち上げて書くと、
三項演算子や `and` / `or` の右側に書かれたときに**評価されないはずの
ものを評価してしまいます**。`ND_LISTCOMP` のような節点を足して、
意味解析と codegen の両方に手を入れるのが筋です（**2 実装ぶん**）。

### 優先度 A-11 — `len` を load にして、境界検査を消す（実装済み ✅）

**レビュー B5「境界検査の分岐がループ本体に残る」の、いちばん多い形が消えました。**

#### 見つけたこと：`for x in xs:` の条件が**毎回の関数呼び出し**でした

`for` は構文解析で `while` に脱糖します。その条件はこうです。

```
while for.ix.0 < len(for.it.0):
```

`len(list)` は組み込みで、**`call @pl_list_len` を出していました**。

```llvm
while.cond.0:
  %t.3 = call i64 @pl_list_len(ptr %t.2)     ; ★ 毎回の呼び出し
  %t.4 = icmp slt i64 %t.1, %t.3
while.body.0:
  %t.8 = load i64, ptr %t.7, !tbaa !5        ; ★ 境界検査は load で読む
  %t.12 = icmp ult i64 %t.11, %t.8
  br i1 %t.12, label %idx.ok.1, label %idx.bad.1   ; ★ 消えない
```

**呼び出しと load が「同じ値」だと分からないので、明らかに範囲内なのに
検査が残っていました。** しかも呼び出しは「メモリを書くかもしれない」ので、
長さの読み出しをループの外へ持ち上げることもできません。

#### 直したこと：`len` を IR に展開する（A-3 と同じ手）

| | |
|---|---|
| `len(list)` | ヘッダのオフセット 8 から `load`（`listhdr` のタグ付き） |
| `len(str)` | ポインタの **8 バイト手前**から `load` ＋ `PL_STR_STATIC`（1 << 62）を落とす `and` |

**最適化後、境界検査も長さの読み出しもループから消えます。**

```llvm
entry:
  %t.4 = load i64, ptr %t.3, !tbaa !0        ; ★ 長さは 1 回だけ
while.body.0:
  %t.15 = getelementptr i64, ptr %t.14, i64 %for.ix.0.012
  %t.16 = load i64, ptr %t.15, !tbaa !3      ; ★ 検査の分岐が無い
```

#### 実測（`-O2`、300 万要素の総和を 10 回）

| | 前 | **後** |
|---|---|---|
| `for x in xs:` | 51.2 ms | **17.6 ms（2.9 倍）** |
| `while i < len(xs):` | 50.4 ms | **17.4 ms（2.9 倍）** |
| 自己コンパイル（型検査まで） | 59 ms | **53 ms** |

**`while i < len(xs)` も同じだけ速くなります。** 標準ライブラリと
コンパイラ自身がこの形だらけなので、全体が少しずつ速くなりました。

#### 検査が消える形／残る形

| 書き方 | 境界検査 |
|---|---|
| `for x in xs:` | ✅ **消えます** |
| `while i < len(xs):` の中の `xs[i]` | ✅ **消えます** |
| `for i in range(len(xs)):` の中の `xs[i]` | ✅ **消えます** |
| `for i in range(n):` の中の `xs[i]`（`n` は別の値） | ❌ 残ります |

**「長さから回る」書き方なら、もう検査は残りません。**
残るのは「別の値から回って添字にする」形だけです（行列積の `range(N)` は
これに当たります）。そこは[ループの分割](#b5-c-だけがベクトル化されています)が要ります。

### 優先度 A-12 — 内包表記（実装済み ✅）

**レビュー D2 でいちばん大きかった穴が埋まりました。**

```python
ys = [x * 2 for x in xs]
odd = [x for x in xs if x % 2 == 1]
sq = [i * i for i in range(5)]
```

#### ⚠️ 構文解析での脱糖には**できません**

`for` 文もカンマ代入も、構文解析で `while` や隠し変数に書き換えています。
**内包表記だけは同じ手が使えません。式の位置に
現れるから**です。文に持ち上げると、こう壊れます。

```python
k = [0] if not cond else [noisy(x) for x in xs]   # ← 内包表記が先に走ってしまう
```

**選ばれない側は評価してはいけません。** そこで節点（`ND_LISTCOMP`）を足し、
**意味解析と codegen がその場でループを組み立てる**ようにしました。

| パス | やること |
|---|---|
| 構文解析 | 形を作るだけ（要素の式・対象・条件・隠し宣言 3 つ） |
| 意味解析 | ループ変数の型を決め、要素の式を**その変数が見える場所で**検査する |
| codegen | 式の位置にループを出す（結果の list を作って push） |
| **所有権検査** | **内包表記の中も見る**（下） |

#### ⚠️ 所有権検査を忘れかけました

意味解析と codegen だけ足した時点で、こう書けてしまいました。

```python
copy_of: list[str] = [s for s in strs]   # 警告なし。--drop を付けると二重解放
```

**同じことを手で書けば警告が出ます**（`for s in strs: copy_of.append(s)` は
E-BORROW-3）。内包表記だけ静かに通るのは、`ownck.c` が新しい節点を
知らなかったからです。ループ変数を「対象の要素を借りている」ものとして
登録し、要素の式を `append` と同じ扱いで見るようにしました。
番人は `tests/cases/warn_listcomp_borrow{{ext}}` です。

**教訓：節点を足したら、パスは 4 つある**（構文解析・意味解析・codegen・
**所有権検査**）。3 つで動いてしまうのが罠です。

#### 入れたもの／入れなかったもの

| | |
|---|---|
| ✅ `[E for x in xs]` / `[E for i in range(a, b, s)]` / `if` での絞り込み | |
| ✅ 入れ子（`[v + 1 for v in [y * 10 for y in xs]]`） | 内側は**式**として書けます |
| ❌ `for` を 2 つ並べる（`[x + y for x in xs for y in ys]`） | 「for は 1 つだけです」と言って落とします。いったん変数に入れてください |
| ❌ 辞書内包・集合内包 | `set` も `dict` のリテラルもまだありません |

⚠️ **`range` の増分は整数リテラルだけ**です（`for` 文と同じ規則。言語仕様 5.5）。

### 優先度 A-13 — `str(float)` が誤差を隠していた（実装済み ✅）

**レビュー C5 を埋めました。** `str(0.1 + 0.2)` は `0.3` ではなく
`0.30000000000000004` です。

```python
print(0.1 + 0.2)    # 0.30000000000000004   ★ 誤差が見えます
print(1.0 / 3.0)    # 0.3333333333333333
print(0.1)          # 0.1                   （17 桁にはなりません）
```

**「17 桁出す」ではありません。** double → 文字列 → double が**元に戻る、
いちばん短い表記**を選びます（Python の `repr` と同じ考え方）。
これで宿題だった「`float` の往復」も片付きました。

#### ⚠️ 素朴なやり方は**測ったら駄目でした**

最初は「10 のべき乗で割って桁を作り、往復するか確かめる」で書きました。
**Python と突き合わせたら 200 件中 116 件しか往復しませんでした**
（正規化と桁の切り出しで 1 ulp ずれる）。

**多倍長整数が要ります。** `runtime/core.c` に 32bit 桁の整数を自前で持ち、
Steele & White / Burger–Dybvig（いわゆる Dragon4）で桁を作ります。
R/S が値そのもの、M± が隣の double との中点までの距離で、
**残りが中点より内側に入った時点で打ち切る**ので最短になります。

| 確かめたこと | 結果 |
|---|---|
| 無作為な double 8005 個（極端な値・非正規化数を含む）で往復するか | **8005 / 8005** |
| Python の `repr` より桁数が多くならないか | **1 件も無し** |

### 優先度 A-15 — 数値計算の手引きと、SIMD の現在地

**「numpy のような計算をどう書くか」に答える文書を作りました。**
→ [docs/reference/numerics.md](reference/numerics.md)（numpy との対応表・実例・
**numpy と違うところ**・ライセンスの出自）。**載せた実例はすべて実際に走らせて確かめました。**

#### ⚠️ 前の章の見立てが間違っていました — 範囲検査はベクトル化を止めていた「主因」ではありません

A-11 では「範囲検査を消せば自動ベクトル化が効くはず」と書きました。**測ったら違いました。**

512×512 の行列積（`list[list[float]]`、`-O2`、Apple Silicon）で、
**実験的に範囲検査の生成を止めて**測った結果です。

| 構成 | 時間 | SIMD 命令数 |
|---|---|---|
| 現状（範囲検査あり） | 220 ms | **0** |
| 範囲検査なし | **145 ms** | **0** |
| 範囲検査なし＋桁あふれ検査なし | 141 ms | **0** |
| 上に加えてループ上限を局所変数に | **130 ms** | **0** |
| C（素朴な三重ループ） | **31 ms** | 20 |

**検査を全部外しても SIMD 命令は 1 つも出ませんでした。**
`-Rpass-analysis=loop-vectorize` に理由を聞くと、こう出ます。

```
loop not vectorized: Cannot vectorize uncountable loop
loop not vectorized: Cannot vectorize early exit loop with more than one early exit
loop not vectorized: cannot identify array bounds
```

つまり止めているものは **3 つ**あり、**全部消さないと 1 つも効きません**。

| 止めているもの | 中身 | 消し方 |
|---|---|---|
| ① 早期脱出が複数 | 範囲検査 1 つにつき panic への分岐が 1 本 | ループ分割（versioning） |
| ② ループ回数が不定 | 上限がグローバル変数だと、本体の書き込みと別名かもしれず読み直しになる | グローバルにも TBAA を付ける |
| ③ 配列の範囲が不明 | `c[i][j]` は「リストの中のリスト」で、内側の先頭番地が毎回 load になる | 内側リストの巻き上げ |

#### ここから引き出した判断

**範囲検査のループ分割（③の宿題）だけを単独で入れても、得られるのは最大 1.5 倍です。**
そして 1.5 倍のためにコード生成のいちばん危ないところ（境界検査の省略）に
手を入れることになります。**費用対効果が合いません。**

**やらないことに決めました。** 代わりに、上の 3 つを**まとめて**外せる見込みが立つまで
待ちます。3 つ全部が消えて初めて C の 31 ms に近づく道が開きます
（＝ 4.7 倍ぶんは検査ではなく**ベクトル化の不在**です）。

⚠️ **この結論は「範囲検査は安い」という意味ではありません。** 35% は確かに払っています。
「**35% のために安全性の要を触るのは割に合わない**」という意味です。

**費用ゼロで効く回避策**は手引きに書きました（ループ上限を局所変数に写す。220 → 205 ms）。

✅ **A-15c で見直しました。** ここの結論（「3 つ全部が消えるまで待つ」）は
`list[list[float]]` に限れば今も正しいのですが、**平坦な `list[float]` では
話がまったく違いました**（境界検査だけで 4 倍）。さらに、止めている
「3 つ」の見立てにも抜けがありました — **負の添字の正規化（`select`）**です。
→ [A-15c](#優先度-a-15c--添字の範囲をループの外で-1-回だけ確かめる実装済み-)

### 優先度 A-18 — 並行実行（スレッド）と、データ競合の検査（実装済み ✅）

**安全性の表で唯一「保証していない」と書いてあった欄が埋まりました。**

| 足したもの | 形 |
|---|---|
| `spawn` | `t: Thread[int] = spawn(work, 1000)` — **新しい構文はありません**（呼び出しの形のまま） |
| `join` | `r: int = t.join()` |
| `mutex[T]` | `m: mutex[Counter] = mutex(Counter(0))` |
| `lock` | `m.lock(bump)` — ロックを取り、渡した関数を呼び、**必ず解く** |
| `sys.cpu_count()` | 使えるコア数（`spawn` の本数を決めるのに使う） |

⚠️ **クロージャが無いので `spawn` は「関数 + 引数 1 つ」**です。複数の値を
渡すときはクラスにまとめます。これは制限ではなく、**渡すものを 1 つの
所有権に集める**ぶん検査に都合が良い形です。

#### 検査 — **注釈は 1 つも増えていません**

| コード | 何を止めるか |
|---|---|
| `E-SEND-1` | 借りをスレッドに渡した（**スレッドは呼び出しより長生きしうる**） |
| `E-SEND-2` | `rc[T]` をスレッドに渡した（参照数の増減が競合する）。⚠️ **`own` で渡すクラスの中に隠れていても**止めます — 型だけ見て「クラスだから安全」とは言えないためです |
| `E-SEND-3` | スレッドから始まる経路でグローバルを書き換えている（⚠️ **呼び先までたどります**） |

🤔 **ここが設計の要点です。** `E-SEND-1` は新しい規則ではありません。
借用検査がすでに持っている「借りは呼び出しより長生きしない」という不変条件が、
そのまま「借りはスレッドに渡せない」に翻訳されただけです。
**規則を足すのではなく、既にある規則の帰結として出てきます。**

さらに **`spawn` を使ったファイルでは、所有権検査が自動でエラーに上がります**
（`--deny-move --deny-borrow --deny-mut` と同じ状態）。既定が警告のままだと
「データ競合が無い」という保証も警告どまりになるためです。`spawn` は新機能なので、
この昇格で壊れる既存コードはありません。

|---|---|---|
| 1 コア | 316 ms | **45 ms** |

#### ✅ scoped spawn で「読み取りの共有」ができるようになりました

```python

    ts.append(spawn(rows, a, b, n, lo, hi))   # ★ a と b は借り。写しを取らない
    ...
# ← ここまでに全部 join されている
```

**ブロックの出口で必ず join する**ので、「借りは呼び出しより長生きしない」という
借用検査の不変条件が**成り立ったまま**になります。規則を緩めたのではなく、
規則の前提を実際に満たすようにした形です。`arc[T]` は要りませんでした。

⚠️ **`spawn` を可変長引数にしました。** 「クロージャが無いので引数 1 つ、

（`E-BORROW-3`）。まとめる形のままでは scoped spawn を入れても借りを共有できず、

⚠️ **可変借用は渡せません**（`E-SEND-4`）。scope: が保証するのは寿命だけで、

書き換えたいものは `own` で渡して `join` で受け取るか、`mutex[T]` に入れます。

⚠️ **途中で抜けられません**（`E-SCOPE-1`）。出口の join が飛ぶと根拠が崩れます。

⚠️ `scope` は**予約語ではありません**（`scope:` の次が改行のときだけブロック）。
このコンパイラ自身が `scope: rc[Scope] | None` を使っているためです。

#### `async` / `await` は入れませんでした

「関数の色が増えるから」の一行で切っていた初版の判断を、
**分析しなおしました**。async には家族が 2 つあり（状態機械型と多重化型）、
色が付くのは片方だけです。**Go と Java 21 は `await` を書かせずに非同期を
達成しています。**

結論は変わりませんが、理由が変わりました。**`spawn` の下を M:N スケジューラに
差し替えれば、利用者のコードを 1 文字も変えずに非同期が得られます。**
`async`/`await` を構文として入れるのは**一方通行の扉**（色は伝染するので
後から外せない）、`spawn` は**両方向の扉**です。
→ [設計 §6](design/concurrency.md)

### 優先度 A-18b — コンパイルを並列にする（実装済み ✅）

**測ったら、コンパイル時間の 95% は `clang` でした。**

| 段 | セルフホスト版一式（11,455 行、14 モジュール、`-O2`） |
|---|---|
| 前段（字句 → 構文 → 意味解析 → 所有権検査 → IR 生成） | **0.17 s** |
| `--check` だけ（IR 生成もしない） | 0.065 s |
| `clang` | **2.9 s** |

つまり**コンパイラ自身をスレッド化しても意味がありません**。

⚠️ **原因は「1 つの `clang` に `.ll` を全部渡していた」ことでした**
（モジュール分割を入れたときからの作り）。clang は入力を順番に処理するので、**コアが 12 あっても
1 つしか回りません**。モジュールごとに `-c` して並べ、最後にリンクします。

| | C 版（stage0） | セルフホスト版（stage1） |
|---|---|---|
| `-j1`（逐次） | 3.58 s | 3.38 s |
| 既定（コア数） | **1.45 s** | **1.83 s** |

**どちらも出来上がる実行ファイルはバイト単位で同一**です（clang は元々、
複数の `.ll` を渡されても 1 本ずつ独立にコンパイルしていました。LTO ではありません）。

⚠️ **上限はモジュール 1 本の時間**です。selfhost なら `sema{{ext}}` の 0.95 秒 +
リンクで、実測の 1.45 秒はほぼ理論値です。ここから先を詰めるには
`selfhost/sema{{ext}}`（IR で 39,865 行）を分割することになります。

#### ⚠️ 最初に書いた形は動きませんでした — スレッド + `system()`

A-18 で入れた `spawn` を使って「スレッドから `sys.run` を呼ぶ」形を先に
書きました。**速くなりませんでした**（CPU 使用率が 92% のまま）。

**macOS の `system()` はシグナル処理を守るためにグローバルなロックを取ります。**
何本のスレッドから呼んでも 1 本ずつしか走りません。`posix_spawn` で
**プロセスを直接起こす**形に書き直したら 12 コアが回りました
（本言語側には `sys.start_shell` / `sys.wait_for` を足しました）。

⚠️ **Windows では逐次のまま**です。`cmd.exe` に `&` による並行実行が無く、
並べるなら Win32 の API を別に書くことになります。
「効かないだけで、壊れない」ほうを選びました。

### 優先度 A-15c — 添字の範囲をループの外で 1 回だけ確かめる（実装済み ✅）

**A-15 の「割に合わない」という結論を、測り直して覆しました。**

平坦な `list[float]` の三重ループ（512×512 の行列積）で測った内訳です。

| 構成 | 時間 | 対 C |
|---|---|---|
| 0.13.1 | 421 ms | 5.8× 遅い |
| 桁あふれ検査なし | 365 ms | 5.0× |
| **境界検査なし** | **89 ms** | 1.2× |
| 境界検査なし + 負の添字の正規化なし（**SIMD 有効**） | **79 ms** | 1.08× |
| C（素朴な三重ループ） | 73 ms | — |

⚠️ **A-15 の「外しても 1.5 倍」は `list[list[float]]` での数字でした。**
平坦な配列では**境界検査だけで 4 倍**です。桁が違います。

#### ⚠️ ベクトル化を止めていた真犯人は、境界検査ではありませんでした

検査を消しても SIMD は 1 つも出ませんでした。理由は**負の添字の正規化**です。

```
addr = data + idx + (idx < 0 ? len : 0)
                    ^^^^^^^^^^^^^^^^^^ この select があると、
                                       LLVM は「添字が 1 ずつ進む」と分からない
```

`xs[-1]` を書けるようにするためのこの `select` が、アドレスをアフィンでなくし、
`cannot identify array bounds` を出させていました。**検査と正規化の両方を
消して初めて `mulpd` / `addpd` が出ます。**

#### もう 1 つ — グローバルにも TBAA を付けました（A-15 の宿題②）

`while i < N:` の `N` がグローバルだと、LLVM は「本体の書き込みが `N` を
書き換えるかもしれない」と見て**毎回読み直します**。するとループ回数が
不定になり（uncountable loop）、版分けをしてもベクトル化できません。

⚠️ A-7 では「グローバルにはタグを付けない。付けないほうが安全側」と
決めていました。**その判断を変えました。** グローバルは `.data` にあり、
`pl_alloc` が返すヒープのオブジェクト（field / listhdr / listelem）とは
**決して重なりません**。だから別の兄弟にしてよいのです
（⚠️ グローバルどうしは同じタグなので、互いに別名かもしれないと扱われます）。

| 512³ の行列積（上限がグローバル `N`） | 時間 |
|---|---|
| タグ無し | 109 ms |
| **グローバルに TBAA** | **53 ms** |
| （参考）上限を局所変数に写した場合 | 41 ms |

#### 入れたもの — ループの版分け（loop versioning）

```
if 全部の添字が両端で範囲内:   検査なしの版（ここがベクトル化される）
else:                        今までどおりの版（診断もそのまま）
```

★ **両端だけ見れば足ります。** 添字が誘導変数について**アフィン**（`A*v + B`）
なら単調なので、途中の値は必ず両端のあいだに入ります。だから
「誘導変数が 1 回しか現れない」形に限っています。

★ 同じ前提から、**負の添字の正規化も消えます**（両端が 0 以上なら全部 0 以上）。
検査と正規化の両方が 1 つの前提で落ちる、というのがこの形の要点です。

⚠️ **診断は変わりません。** 範囲外になるループは今までどおり、ちょうどその
反復で、同じメッセージで止まります。両端の計算で桁あふれしたときも、
ガードを落として遅い側へ行かせます（そちらが正しく panic します）。

適用するのは、**呼び出しも入れ子ループも脱出も無い**「数える形」のループだけです
（呼んだ先が `append` すれば長さが変わり、前提が崩れるため）。

#### ⚠️ 実装中に自分で作った穴を 1 つ塞ぎました

最初の版は「添字が誘導変数についてアフィン」しか見ていませんでした。
ところが

```python
while j < n:
    s = s + xs[k]
    k = k + 1        # ← k がループ内で変わる
    j = j + 1
```

の `xs[k]` は「j についてアフィン」です（j が現れない＝定数項）。
**両端で確かめた値と実際の値が違い、範囲外を読んで通ってしまいました。**
「**誘導変数以外は不変**」を要求するよう直しました
（`tests/cases/rt_vz_moving{{ext}}` が回帰テストです）。

#### 結果（`bench/run.sh mat`。512³、5 回の最小）

| | 時間 | 対 C |
|---|---|---|
| C 平坦配列 -O2 | 31.3 ms | — |
| **本言語平坦 `list[float]` -O2** | **39.6 ms** | **1.27 倍** |
| 本言語二重リスト -O2 | 206.7 ms | 6.6 倍 |
| 本言語 linalg.Matrix -O2 | 521.7 ms | 16.7 倍 |
| Python 3 | 17807 ms | 569 倍 |

⚠️ **効くのは平坦な `list[float]` だけです。** 二重リスト（`list[list[float]]`）は
内側リストの先頭番地が毎回 load になるので（A-15 の③）、この版分けでは
届きません。`linalg.Matrix` は `get` / `set` がメソッド呼び出しなので、
版分けの条件（本体に呼び出しが無い）から外れます。**そこは次の宿題です。**

### 優先度 A-19 — GPU

**まだ設計だけです。** LLVM IR を出す処理系なので、道は 2 つあります。

| 道 | 中身 | 見立て |
|---|---|---|
| ① SPIR-V / PTX を直接出す | `gpu:` ブロックの中だけ別ターゲットへコード生成 | **本命**。LLVM に両方のバックエンドがある |
| ② 外部カーネルを `extern` で呼ぶ | CUDA/Metal のカーネルを別に書いて繋ぐ | 早いが「自前で完結」から外れる |

**先に片付ける前提が 2 つ**あります。**(a) ベクトル化（A-15 の 3 つ）** と
**(b) 並行実行（A-18）**。GPU は「並列に書ける形」が言語側に無いと足せません。
**(b) は入りました**（`spawn` / `join` / `mutex[T]`）。残るは (a) です。

### 優先度 A-20 — 組み込みと OS レベル

**すでに土台はあります**（`unsafe:` ／生ポインタ／volatile ／インライン `asm` ／
RISC-V ベアメタルの CI）。ここから先に足すもの：

| 足すもの | なぜ |
|---|---|
| `#[interrupt]` 相当の関数属性 | 割り込みハンドラは呼び出し規約が違う |
| リンカスクリプトの同梱と `--target` の整備 | いまはユーザが用意している |
| **ヒープ無しモード**（`--no-heap`） | `list` / `str` を静的な容量に縛る。**動的確保が禁止の現場向け** |
| `volatile` の型付け（`mmio[T]`） | いまは `unsafe:` の中で生ポインタを触っている |
| スタック使用量の静的な上限 | 再帰が無ければ計算できる |

⚠️ **ヒープ無しモードは言語の意味を変えます**（`append` が失敗しうる）。
入れるなら[§0 ①](#①-書きやすさが下がるならその安全機能は入れない)に照らして
「**モードを分ける**」形にします。既定の書き味は変えません。

### 速さ

**0.4.0 で 3 つの O(n²) を潰しました。** どれも「測っていなかった」ことが
原因です（`strings{{ext}}` の冒頭には「速度はセルフホスト後に測ってから直す」という
コメントが残っていました）。

| 箇所 | 原因 | 効果 |
|---|---|---|
| `strings.substr` | 1 文字ずつ連結 | 20000 語の分割 7.2 秒 → 0.00 秒 |
| `dict.remove` | 毎回詰め直し | 実用例 115 秒 → 0.19 秒 |
| `Token.init` | トークンごとにソース全体を複製 | 自己コンパイル 3.8 秒 → 0.32 秒 |

現在の水準：

| | |
|---|---|

### A. 前の章の結論が間違っていたもの

#### A1. ⚠️ 「TBAA は効かない」は誤りでした

A-4 では「別名解析を試したが 142 → 146 ms でゼロだった」と書きました。
**これは、そのときのボトルネックがインライン化だったからです。**
`cold` を入れて詰まりを取ってから測り直すと、**効きます。**

| | TBAA なし | TBAA あり |
|---|---|---|
| `linalg.Matrix` の行列積 | 60 ms | **48 ms**（−20%） |
| 二重リストの行列積 | 43 ms | **36 ms**（−16%） |

**教訓：「効かなかった」は「そのときのボトルネックでは効かなかった」でしかありません。**
ボトルネックを 1 つ外したら、前に否定した案をもう一度測るべきでした。

**✅ 入れました**（[優先度 A-7](#優先度-a-7--別名解析tbaa実装済み-)）。
⚠️ ただし効きは **−8%**（`linalg`）で、下の −20% より小さく出ました。
この試作は**A-6 の前**に測ったものだからです。

**入れ方（試作で確認済み）：** 型タグを 3 つに分けます。

```llvm
!0 = !{!"<言語名>"}              ; 根（langinfo が決める）
!1 = !{!"field",    !0}            ; クラスのフィールド
!2 = !{!"listhdr",  !0}            ; list のヘッダ（data ポインタと len）
!3 = !{!"listelem", !0}            ; list の要素
```

健全性は確認しました。`pl_list_new` はヘッダと要素配列を**別々に確保**するので
（`runtime/core.c`）、この 3 つは決して重なりません。`unsafe:` の生ポインタ・
`extern` 関数・文字列にはタグを付けません。**タグの無いアクセスは
「何とでも別名かもしれない」と扱われる**ので、付けないほうが安全側です。

⚠️ **ただしベクトル化は起きません**（下の B5）。TBAA が外すのは
ヘッダの読み直しであって、境界検査ではありません。

### B. ベンチマークの信頼性

#### B1. ⚠️ 「C の 5.1 倍」は起動時間の引き算が効きすぎた数字です

いまの計測方法は「総時間からプロセス起動 4 ms を引く」です。
**ところが C 側の総時間が 9 ms しかありません。** 4 ms を引くと 5 ms になり、
**分母が半分になります。** 分母を半分にしてから比を出しているので、
比が実際より小さく出ます。

**起動が無視できる大きさ（N=512）で測り直しました。**

| | N=256（起動を引く） | **N=512（引き算なし）** |
|---|---|---|
| C 平坦配列 | 6 ms | 38 ms |
| 本言語二重リスト | 36 ms（**6.0 倍**） | 295 ms（**7.8 倍**） |
| 本言語 `linalg.Matrix` | 55 ms（**9.2 倍**） | 450 ms（**11.8 倍**） |

**正直な数字は「C の 8 倍（二重リスト）／12 倍（`linalg`）」です。**
比は N を 2 倍にしてもほぼ変わらないので、**256 の数字がキャッシュの
都合で得をしているわけではありません**（この点は疑いましたが、白でした）。

**✅ 直しました。** どのプログラムも**自分の中で時計を読み**、
測りたいループだけを `TIME_MS` として出します（本言語は `lib/time{{ext}}`、
C は `bench/bench_time.h`、Rust は `Instant`、Python は `perf_counter`）。
引き算はもうありません。N も 512 にしました。起動時間は
「何もしないプログラム」の行として**別に**出します（約 5 ms）。

#### B2. ⚠️ 見出しの数字はすべて `-O2`。既定は `-O0` です

README のとおり `{{cc}} prog{{ext}}` と打つと `-O0` になります。

| | `-O0`（既定） | `-O2` |
|---|---|---|
| `linalg.Matrix` の行列積 | **459 ms** | 60 ms |
| 二重リストの行列積 | **162 ms** | 41 ms |

**利用者がふつうに得るのは 459 ms のほうです。** 7.7 倍の差があります。
ロードマップの数字はどれもこの差を書いていません。

**✅ ②と③をやりました。** `bench/run.sh` の表は `-O0`（既定）と
`-O2` を**別の行**にして出します。この文書の数字にも `-O2` と書いています。
**①（既定を変える）はしていません。** 既定が `-O0` なのは、
コンパイルが速いほうが書いている最中は嬉しいからです。

#### B3. ⚠️ `bench/` が `.gitignore` にあります

**この文書の数字は、誰も再現できません。** 計測コードがリポジトリに
入っていないためです。「ベンチマークのコードは git から除外」という
当初の指示によるものですが、**結果を公開文書に載せるなら再現手段も要ります。**

**✅ 追跡するようにしました**（`bench/` のソースと `bench/README.md`。
作った実行ファイルだけ `bench/out/` に入れて除きます）。`bench/run.sh` は
`rustc` / `python3` / `numpy` が無くても動きます。

#### B4. ⚠️ 番人テストは時間を検査していません

`list_index_perf{{ext}}` と `linalg_matmul_perf{{ext}}` は**出力しか見ていません。**
10 倍遅くなっても**通ります。** 人がテスト全体の所要時間の変化に
気づくことに頼っています。「番人」と呼ぶには弱いものです。

**✅ 直しました。** `lib/time{{ext}}` が入ったので、2 つの番人は
**比**を検査します（機械の速さに依らせないため）。

| テスト | 見る比 | いま | 壊れると | しきい値 |
|---|---|---|---|---|
| `list_index_perf{{ext}}` | 添字ありの行列積 / 添字なしの同回数ループ | 3.5 | 11 | 7.0 |
| `linalg_matmul_perf{{ext}}` | `linalg.Matrix` / 平坦な直書き（**ひどい遅さだけ**を見ます） | 1.1（macOS）/ 3.6（Linux） | — | 6.0 |

**番人が本当に鳴ることも確かめました**（`-mllvm -inline-threshold=120` で

#### ⚠️ 「インライン化されたか」を**時間で**測るのはやめました

CI に 2 回叱られました。どちらも Linux（Ubuntu clang 18.1.3）で鳴り、
**しかしインライン化は効いていました。**

| 比べ方 | macOS（Apple clang 21） | Linux（clang 18） |
|---|---|---|
| ① `linalg` / 二重リスト | 2.1 | **4.28** |
| ② `linalg` / 平坦な直書き | 1.07 | **3.57** |

- ①は**データの並べ方まで違います**（平坦 vs 二重リスト）。
- ②は同じ並べ方にしましたが、**直書き側は `N` が定数畳み込みできます**。
  ストライドが定数か実行時の値かで、最適化のかかり方が変わります。

**「差が 1 つだけ」の相手を、時間で作るのは難しい**という結論です。

**構造で見ることにしました。** `make inline-check` が
`clang -Rpass-missed=inline` に直接聞きます。**機械にも版にも依りません。**

```console
$ make inline-check
★ linalg.Matrix.get / set は畳まれています（Apple clang version 21.0.0）
```

CI（3 OS）で毎回走ります。番人テストのほうは
「**ひどく遅くなっていないか**」だけを見る役目に下げました（しきい値 6.0）。

⚠️ **副産物として分かったこと。** Linux では `linalg.Matrix` の行列積が
平坦な直書きの **3.6 倍**です（macOS は 1.1 倍）。畳まれてはいるので、
**別の理由**（ストライドが実行時の値だとベクトル化が開かない、など）です。
[B5](#b5-c-だけがベクトル化されています)の続きとして調べる価値があります。

#### B5. C だけがベクトル化されています

⚠️ 内側ループの SIMD 命令の数を数えました。

| | SIMD 命令 |
|---|---|
| C（平坦・二重ポインタとも） | **8** |
| 本言語 `linalg` | 2 |
| 本言語二重リスト | **0** |

**境界検査の分岐がループ本体に残るため**、LLVM がベクトル化できません。
最適化後も `pl_index_fail` への分岐が 9 か所残ります。
**TBAA を入れても検査の数は変わりません**（9 か所のまま）。
残り 8〜12 倍の差の主因はここだと考えられます。

⚠️ [§0 の ②](#0-この言語が譲らないこと)により、**検査を外す `unsafe` な添字は
入れません。** 必要なのは「検査をループの外へ出す」ことです
（帰納変数の範囲から自明に安全と分かる場合に、検査つきの本体と
検査なしの本体へループを分割する）。

#### ✅ いちばん多い形は片付きました

`for x in xs:` と `while i < len(xs):` の中の `xs[i]` は、**検査ごと消えます**。
`len` を load に展開して、条件と検査が同じ値を見るようにしたためです
（[優先度 A-11](#優先度-a-11--len-を-load-にして境界検査を消す実装済み-)）。

**残っているのは `for i in range(n)` の中の `xs[i]` です**（`n` と `len(xs)` の
関係を LLVM は知りません）。行列積はこちらなので、以下はまだ有効です。

#### ⚠️ LLVM の既製のパスでは外れませんでした

「LLVM に既にある IRCE（Inductive Range Check Elimination）を有効にすれば
済むのでは」を試しました。**外れません。**

```bash
opt -passes='default<O2>,function(irce)' -irce-print-range-checks prog.ll
# → 候補すら見つからない（何も出ない）
```

- Apple clang は `-mllvm -enable-irce` を持っていません（Homebrew の LLVM 22 で試験）
- `loop-versioning-licm` も同じく効きません

**一方で、良い知らせが 2 つあります**（最適化後の IR を読んで確認）。

1. **負の添字の正規化（`select`）は消えています。** `for i in range(N)` の
   `i` は非負だと LLVM が分かるので、検査は素の `icmp ult %iv, %len` です。
2. **ループ不変な検査はすでに前置ヘッダへ持ち上がっています。**

残るのは「`N <= len(xs)` を証明できない」ぶんだけです。`N` はグローバル、
`len` は実行時の値なので、**証明ではなくループの分割（versioning）**が要ります。

**つまり、自分で書くしかありません。** 設計の要点は次の 2 つです。

| 要点 | 内容 |
|---|---|
| どこに出すか | `for i in range(a, b)` の入口で `b <= len(xs)` を 1 回検査し、成り立てば**検査なしの本体**、成り立たなければ**いまの検査つきの本体**へ分岐する |
| ⚠️ 健全性の条件 | ループの中で `xs` が**短くならない**こと。`append` / `remove` はもちろん、**`mut` で渡す呼び出し**でも変わりえます。効果の解析が要ります（この言語には `mut` 注釈があるので土台はあります） |

#### B6. 比較対象が足りません

| | 状態 |
|---|---|
| Rust | **未実施**（開発機の `rustc` が 1.50 でリンクできない） |
| numpy | `a @ b` は **BLAS**（ブロック化・SIMD・マルチスレッド）。**同じ土俵ではありません** |
| 並列 | 本言語に並行実行がないので**単スレッド同士の比較**である旨の明記が要ります |

#### B7. ✅ 疑ったが白だったもの

- **「構築の時間が混ざっているのでは」** → 積を外した版と差を取ったところ、
  構築は **2 ms** でした。測っているのはほぼ積です。**問題なし。**
- **「自己コンパイル 1.4 倍」** → 実測 C 57 ms / stage1（`-O0`）78 ms で
  **1.37 倍**。**記述どおりです。**
- **「N=256 はキャッシュに載るから得をしている」** → N=512 でも比はほぼ同じ。
  **問題なし。**

### C. 安全性の穴 — 整数があふれても黙っています（解消済み ✅）

> **✅ この節の指摘は 0.6.0 で埋めました。**
> `+` `-` `*` `**` `int()` が桁あふれで panic します。折り返しは `wrap_*`。
> [優先度 A-5](#優先度-a-5--整数のオーバーフロー実装済み-) を見てください。
> ⚠️ ただし**速さの代償は当初の見積り（2.4%）より大きく**、`linalg.Matrix` の
> 行列積が 2.5 倍遅くなりました（原因はまたインライン化です）。以下は当時の記録です。

⚠️ **先に公平を期します。これは書き忘れではなく、仕様に明記された v1 の判断です。**

> `int` … 64bit 符号付き整数。**オーバーフローは 2 の補数でラップ**
> （[language-spec.md 3.1](spec/language-spec.md)）
>
> **⚠️ 保証しないこと**：整数オーバーフロー（v1 どおり 2 の補数で回る）
> （[safety-spec.md 1](spec/safety-spec.md)）

`lib/random{{ext}}` の線形合同法は**この折り返しを使って書かれています**
（「これが法 2⁶⁴ の計算そのものになる」）。つまり**意図的な仕様**です。

**それでも問題として挙げます。理由は 3 つです。**

1. [§0 の ②](#0-この言語が譲らないこと)（安全性が下がるならその書きやすさは
   入れない）と衝突します。`null` を型で防ぐ言語が `a * b` の符号の反転を見逃します。
2. **README とロードマップの見出しは「世界一安全な言語」です。** 仕様の奥に
   書いてあっても、掲げているものとの落差は残ります。
3. **0.5.1 で一貫性が壊れました**（下）。

以下は実測です。

| 式 | 本言語 | あるべき姿 |
|---|---|---|
| `9223372036854775807 + 1` | **`-9223372036854775808`** | panic |
| `9223372036854775807 * 2` | **`-2`** | panic |
| `2 ** 63` | **`-9223372036854775808`** | panic |
| `2 ** 64` | **`0`** | panic |
| `0 - (-9223372036854775808)` | **`-9223372036854775808`** | panic |
| `int(1.0e30)` | **`-9223372036854775808`** | panic |
| `1.0 / 0.0` | **`inf`** | 要検討（Python は例外） |
| `0.0 / 0.0` | **`nan`** | 要検討（Python は例外） |

#### ⚠️ 0.5.1 で一貫性が壊れました

`-9223372036854775808 // -1` を panic にしたときに、
**同じ「64bit に収まらない」なのに `//` は落ちて `*` は黙る**状態を作りました。
`1 // 0` は落ちるのに `1.0 / 0.0` は `inf` を返します。

**どちらに揃えるかを決める必要があります。** 揃っていないのがいちばん悪い状態です。

#### ⚠️ 入れるなら「意図的に折り返したい」場所の逃げ道が要ります

`lib/random{{ext}}` が実例です。線形合同法は**法 2⁶⁴ の計算そのもの**として
折り返しを使っています。検査を既定にすると、**標準ライブラリが panic します。**

つまりこれは「検査を足す」だけの話ではなく、
**「折り返しをどう書き分けるか」という言語設計の判断**です。設計案は下の E を
見てください。

**⚠️ 速さとも衝突します。** 検査つき算術（`llvm.sadd.with.overflow` など）は
加算・乗算のたびに分岐が増えます。行列積の内側ループに入ります。

#### C5. `str(float)` が誤差を隠します（解消済み ✅）

> **✅ この節の指摘は 0.9.0 で埋めました。**
> `str(0.1 + 0.2)` は `0.30000000000000004` です。
> [優先度 A-13](#優先度-a-13--strfloat-が誤差を隠していた実装済み-) を見てください。
> 以下は当時の記録です。

`str(0.1 + 0.2)` は **`0.3`** を返します（6 桁で丸めるため）。
Python は `0.30000000000000004` です。
**数値計算の言語として、利用者が自分の誤差を見られないのは問題です。**
`float → str → float` が元に戻らないことは既に宿題に挙がっていますが、
**「誤差が見えない」という害のほうが大きい**と考え直すべきです。

| ~~6~~ ✅ | ~~**演算子オーバーロードと `m[i, j]`**~~ → **実装済み**。意味解析の読み替えだけで、codegen は無変更 | D1 |

⚠️ **1 と 5 は衝突します。** オーバーフロー検査は内側ループに分岐を足し、
境界検査の追い出しは分岐を減らします。**両方を同じ「ループの外へ出す」
仕組みで扱えないか**を、設計のときに一緒に考えるべきです。

## 4. 設計上ぶれさせないこと

新しい機能を足すときも、この 5 つは変えません。

1. **暗黙の型変換をしない。** `int` と `float` すら混ざりません。
2. **GC を入れない。** 所有権と `rc[T]` で足りるようにします。
3. **例外でスタックを巻き戻さない。** `raises` は戻り値の検査です。
4. **呼び出し側に印を書かせない。** `&x` も `x.clone()` も不要にします。
5. **2 つの実装を一致させ続ける。** C 版とセルフホスト版が同じ IR を出すこと（`make test`）、
   そして stage2 == stage3（`make bootstrap`）を壊さないこと。
